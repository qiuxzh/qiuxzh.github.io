05 知识存储技术

qiuxz2026-11-062026-11-06

第三章从两句话里抽出了二十一条三元组，第四章把它们对齐成了同一套实体编号。这一章要回答的是这二十一条记录最后以什么形状落在磁盘上。同一批数据摆法不同，一条查询要读几次盘，要走几次索引，又要写几份副本，全都跟着变。全章用王健林这张小图跑三条查询，分别是直接邻居、三跳路径和事件聚合，看每种布局在哪一条上吃亏。

知识存储：三元组落在磁盘上的形状

存储方案之间的差别只有一件事，就是把图里的实体和边摆到磁盘的什么位置。摆法决定了寻址方式，寻址方式决定了查询代价。

输入：二十一条三元组与两套编号

送进存储层的是第三章留下的成品。十个实体与十一个谓词，二十一条三元组，外加一个带四个槽位的签约事件。

存储层不认中文字符串。先编号，同一条事实在磁盘上就是三个整数，比较和排序都变成整数运算。

输出：一种布局与三条查询的代价

这一节的输出有两样。一样是某种存储布局，另一样是三条查询在这个布局下的执行代价。

三行查询里有五个格子标了橙色。三元组表输在多跳，属性表输在跨类型，二元表输在聚合。

三条查询：一跳、多跳与聚合

三条查询分别压三种访问模式。邻接查询只碰一个节点的邻居，路径查询要顺着边走好几步，聚合查询要扫一批边再计数。

三条查询对应三种访问模式。Q1 只看一个节点的邻接表，Q2 要看三层的邻居，Q3 要把某个主语的所有边扫一遍。

Q1 从王健林出发，沿五条边各走一步。任职于通到万达集团，父子通到王思聪，职务通到董事长，出席通到签约事件。Q2 有两条路，一条两跳经过万达集团，一条三跳经过万达集团与星光影视。Q3 只在万达集团这个主语上筛谓词为参与的行，命中一条。

三元组表：三列一张表

最省事的存法是把每条三元组写成一行，整张图变成一张三列的关系表。图里的边变成行，行与行之间没有任何物理联系。

主键与索引：三列怎么排

主键取三个字段的组合。同一个主语可以有很多条边，同一个谓词可以出现在很多行，只有三者合起来才唯一。

三列结构本身不提供任何加速。真正撑起查询的是旁边这三份索引，一份按头，一份按谓词，一份按尾。

索引是这张表能用的前提。没有索引，每次查询都要全表扫描；有了索引，按实体或按关系都能快速定位。代价是存储变大、写入变慢，因为每插一行都要维护索引。

四种布局跑同一条一跳查询

Q1 只问王健林有哪些邻居，四种布局的执行路径完全不同。同一句话在磁盘上变成四条不同的读法。

四个面板答的是同一道题。属性表最快却答不出，三元组表答得出但要三层索引，邻接一跳到位但要遍历链。

一次自连接换一跳

想从万达集团走到它的合作方，再用合作方的编号回同一张表里找下一跳，只能把表和自己拼起来。一次自连接就换一跳。

SQL 里的 JOIN 关键字就是图里的一次跳。跳数写在 FROM 子句里，跳得越深，子句越长。

三元组表的三处开销：稀疏、演化与跳数

三元组表在原型阶段很好用，规模上去之后三个问题会依次冒出来。它们分别来自谓词数量、schema 变更和跳数。

谓词透视：一百一十格填二十一格

把谓词透成列，一张表就变成实体乘谓词的矩阵。这张矩阵里九成的格子是空的。

矩阵里二十一个蓝格子就是二十一条三元组。剩下八十九格没有事实可填，但宽表照样要为它们留位置。

schema 演化：加一个谓词要动什么

图谱会长出新谓词。三元组表只需多插几行，宽表得改结构，还得回头给历史数据补空值。

左边多一行，右边多一列。多个一行是数据变动，多个一列是结构变动，后者的代价高一个量级。

自连接：每跳乘三

跳数才是三元组表真正的天花板。起点有 3 个分支，三跳之后就是 27 条路径要拼。

每一跳都把上一层的行数乘上分支数。第一跳 3 行，第二跳 9 行，第三跳 27 行，SQL 里对应三个 JOIN，中间结果全部要落地。

递归查询在 SQL 标准里有，各家实现差异大，优化器也不擅长它。写法上还能看出成本，两跳要自连接，三跳要三张表连起来，四跳往上 SQL 基本没法读。

属性表：一行一个实体

按实体类型拆表，一类实体一张宽表，一个实体占一行。这是关系建模里最成熟的套路，也是绝大多数业务系统默认的样子。

宽表：一行装下全部属性

人物有姓名和年龄，企业有成立年和行业。同一类的实体把属性摊成列，一次主键查找就能把整行取回来。

宽表的行是实体，列是属性。它的查询优势和它的空值劣势来自同一个决定：把属性提前固定成列。

同一个类型里的实体，属性集合很少完全一致，宽表只能取并集，用不上的位置填 NULL。

列一多，行就稀疏，查询要跳过大量空位，空间和速度都被拖累。真实图谱里一个人可能有二十个可选属性，实际平均用到四个，空位占九成。

空值的根源是「提前定列」，与数据质量无关。行宽按最全的那个实体算，最瘦的实体也得占这么宽。

跨类型查询要 union

麻烦出在跨类型上。要找「总部在上海的主体」，三类实体分在三张表里，得写三段查询再合起来。

属性表把「实体是什么」和「实体之间怎样」一起按类型切开。类型一多，跨类型的问句就得靠 union 拼回去。

二元表：每个谓词一张两列表

把关系单独拿出来，一个谓词一张表，每张表只有两列。这一招叫垂直划分，也叫二元表。

结构：两列存头尾

合作是一张表，父子是一张表，注册地又是一张表。表里只有两个整数，头编号与尾编号。

二元表把稀疏问题彻底解决了，代价是表的数量跟着谓词数量走。谓词在知识图谱里是会长的那一类东西。

二元表在存储效率上确实赢。每张表只装真正存在的事实，行数等于该谓词的边数，一列空值都没有。

写入也更好办。新增一个谓词只是新建一张小表，不动任何老表，历史数据一行都不用回填。

代价：表数量等于谓词数量

麻烦落在查询侧。Q3 要数万达集团参与的事件，还只是两张表。真实问句常常跨五个谓词，那就是五张表的 join。

表名还得靠程序拼字符串。谓词是数据，表名却在代码里，加一个谓词就要改一次查询构造逻辑。

连接顺序也影响中间结果。五张表先连哪两张，计划器要估代价，估错一次中间结果就翻十倍。

索引表：三种建法

不管用哪种组织方式，真正决定查询快慢的是索引。索引表是一种显式做法，单独一张表，一列存查询键，一列存记录引用。

穷举索引：三个方向全建

索引表的形状很简单，一列存查询键，一列存记录的引用。先查索引拿到编号，再按编号回主表取整行。这一步叫回表。

三元组有三个位置，任意一个都可能出现在查询条件里。穷举索引把三个方向都建成一份。

绿色是可以直接定位，橙色是还要扫。三种建法的差别，就是橙色格子有多少。

谓词索引与复合索引

谓词索引按谓词分组。谓词只有十几到几十个，组数不多，每组内部再建一棵 B 树，体积比穷举小很多。

复合索引在穷举之上多存一列实体类型。查「所有企业类型的合作方」时，类型列可以直接过滤，少读一半的数据块。

索引键的选择有两条标准，查询频率高，取值重复度低。姓名比性别更适合建索引，因为性别只有两个取值，扫一半的行跟全表扫差别不大。

写入放大：一次插入写四处

索引不是免费的。每多一份索引，写入就多一次页更新。

一条事实落盘变成四次页写。索引表不改变主表结构，只是在旁边加了几条快速通道，通道本身也要维护。

三种关系库方案各管一段。三元组表管灵活，属性表和二元表管结构清楚，索引表管查询速度，它们可以在同一个库里并存。三者共享同一个上限，每次跳转都要经过一次索引查找。

免索引邻接：指针代替查找

关系库里找王健林的邻居，每一跳都要查一次索引。图数据库换了个思路，把邻居直接记在节点身上，这一招叫免索引邻接。

节点持有邻居地址

节点记录里存一个指针，指向它的第一条关系的物理位置。关系记录里再存一个指针，指向同一个起点的下一条关系。

节点定长、关系定长，是这套设计成立的前提。定长意味着位置可以用偏移量算出来，不必扫描。

局部子图与全图规模

跳转的成本只跟这一跳能走到几个邻居有关，跟库里有一亿还是一千亿个节点无关。这是两种库真正的分水岭。

关系库的成本随跳数线性累加，每一跳都要跟全表规模打交道。图库的成本只跟这一跳能走到几个邻居有关。

Q2 走这条优势最明显。三跳之后关系库已经读了 39 页，图库只读了 6 页，而且第二组数字不会因为图谱长大而变。

双向指针的代价

指针不是白来的。为了让反向查询也快，每条边存两个方向，插入时要同时改好几处。

指针把读做便宜了，把写做贵了，也把分区做难了。这三个代价经常被忽略，因为演示数据的写入量总是很小。

物理布局：行存、列存与落盘

要让指针成立，磁盘上得专门设计文件结构。主流原生图库把数据分成三类存储块，各自定长，各自连续。

三类存储块：节点、关系与属性

节点一个文件，关系一个文件，属性又一个文件。三类各自连续存放，靠偏移量互相引用。

定长与连续，再加上可算偏移，这三件事让「按编号直接寻址」成立。属性长度不定，于是单独放一片，用块号引用。

内联属性与动态属性

属性长度不定，放法有两种。小的跟着节点走，大的单独放一片，节点里只留一个引用。

内联省一次跳转，动态省空间。两种都留着，是因为一个图谱里同时存在这两类属性。

一次跳查询的三次 IO

把一次一跳查询拆到磁盘层面，能看到三页数据依次进内存。第一页是名字索引的叶子，第二页是节点记录，第三页是那条邻接链。

缓存能把第二次以后的重复访问省掉。批量查一千个起点时，第一页可以合并成一次前缀扫描，热点节点的节点页也常常还在内存里。

遍历的顺序顺着这个结构走。读节点，定位起点，加载标签与属性，取邻居，预加载缓存，到终止条件返回。

Cypher：路径模式匹配

Cypher 是 Neo4j 的查询语言，特点是用 ASCII 字符把图直接画出来。节点用圆括号，关系用方括号加箭头，模式长什么样，语法就长什么样。

模式匹配：节点、关系与路径的写法

MATCH (a)-[:合作]->(b) 这行字本身就是一张图。圆括号是节点，方括号是关系，箭头是方向。

声明式的意思是只描述要找什么形状的子图，不写怎么遍历。走法由引擎决定，这也是它比手写 JOIN 短的原因。

变长路径与常用子句

路径长度写成 *1..3，意思是走一到三步都算命中。引擎按层展开，每层去重一次。

变长路径把「跳几步」从语法结构变成了参数。代价从写 SQL 转移到运行时，参数给大了照样拖库。

删除有一个坑。DELETE 只删节点本身，节点上还连着关系时会被拒绝；DETACH DELETE 才会把关系一起带走。MERGE 的语义是「不存在才创建」，适合重复执行而不产生副本的场景。

Neo4j 的版本和 JDK 版本必须对得上。5.x 要 JDK 17，4.0 到 4.4 要 JDK 11，3.5 要 JDK 8。社区版单个实例可以撑到 320 亿节点和关系，默认端口 7474，初始账号密码都是 neo4j。

SPARQL：三元组模式与连接

RDF 这一支用 SPARQL。它不画图，只写三元组模式，变量用问号开头，多个模式共享变量就等于 join。

基本图模式：三元组模式与变量绑定

一个三元组模式就是一条带变量的三元组。写成三段，中间用点号隔开，合起来叫基本图模式。

SPARQL 的连接靠同名变量。两个模式都出现 ?org，引擎就把它们接在一起，不用写 ON 条件。

与 Cypher 的等价表达

同一件事有两种写法。万达集团的两跳合作方，Cypher 用一条路径模式，SPARQL 用三个三元组模式。

前者的可读性来自形状本身，后者的可读性来自每行只有三个位置。两种语言都能表达一跳与多跳，区别在引擎怎么执行那条路径。

三代演进：从关系表到原生图库

图数据库不是一步到位的。三代解决的是三个不同的问题，留下的短板也各不相同。

第一代：关系库与三元组表

最早的一代直接架在关系库上。三元组表与属性表，还有二元表，都是那个时期的产物，RDF-Store 也是这么起来的。

好处是复用了成熟的事务与备份体系。短板是多跳，这一点本章前半部分已经算过。

第二代：原生图库与分布式非原生

第二代把存储引擎重写，让指针成为一等公民。Neo4j 是这一代的代表。它把全局索引从读路径上拿掉了。

同一条时间线上还有另一支，把图切到多台机器上，用分布式 KV 存邻接表。规模解决了，多跳又慢回去，因为每次跳转都要跨网络。

三代的分界线是原生存储和分布式。两样都要，得等到存储引擎重新设计，把指针换成可路由的分片键。

第三代：原生分布式图库与 RDF-Store

第三代要同时拿到两样东西，原生存储的遍历速度与分布式的规模。做法是把邻接指针换成分片键，每个节点带着自己的分区标记，跨分区的那一跳走网络。

NebulaGraph 与 TigerGraph 属于这一代。一条三跳查询里，前两跳可能落在同一台机器上，第三跳跨到另一个分区；代价从「指针解引用」变成「一次 RPC」，但总算不用把整张图塞进一台机器。

RDF 这条线同期往前走。Jena 的 TDB 用三元组索引做子图匹配，Fuseki 在其上提供 SPARQL 端点；Virtuoso 把三元组压成列存再 join；gStore 走另一条路，把 SPARQL 查询编译成子图匹配，在图结构上剪枝减少候选。它们守的是标准与可移植性，性能通常比原生图库差一档。

三代的分界线渐渐模糊。2020 年之后的产品普遍同时支持点查、多跳与批量分析，选型回到数据规模与查询形状这两个原始问题上。

选型：五个维度与一条判断线

选型看五件事，数据规模与查询形状，写入比例，事务要求，生态与运维成本。前两个决定合不合适，后三个决定划不划算。

布局 存储单元 稀疏与空值 多跳代价 写入代价
三元组表 一行一条事实 三列无空值，谓词多了索引膨胀 每跳一次索引，三跳 39 次页读 一次插入写主表与三份索引
属性表 一行一个实体 属性参差就出 NULL，密度可低到一成 仍要逐跳定位，实体类型多还要 union 加属性要改表，历史行要回填
二元表 一表一个谓词 两列全满，无空值 涉及几个谓词就要 join 几张表 新增谓词建一张小表，不动老表
免索引邻接 节点加关系定长记录 属性走动态块，节点保持定长 一跳一次链式读，与全图规模无关 一条边改四处指针，跨分区更贵

四种布局没有优劣，只有匹配。判断的入口是查询形状，不是数据量大小。

判断的切入点是查询形状。业务查询大多是一两跳，带强过滤条件，还要事务保证对账，关系库更合适，也没必要迁移。查询经常要「走三步以上看能到谁」，比如资金流向与担保链，还有设备故障传播，图库的优势才显出来。

维度 关系库 原生图库 分布式图库
数据规模 单机到千万行 单机到百亿节点 从十亿起，可到千亿
查询形状 一跳为主，带强过滤 三跳以上的路径为主 深链加全图分析
写入比例 事务型写入频繁 读多写少 批量导入加流式追加
事务要求 强一致，成熟 单机强一致，跨机弱 最终一致或分片事务
生态与运维 工具齐全，人才多 运维经验少，监控要另搭 组件多，排障链路长

五个维度里，规模和查询形状是硬约束，写入比例与事务，还有运维，都是成本项。

还有一个现实约束是团队。图数据库的运维与备份，监控与权限体系，跟关系库是两套经验。迁移的代价不只在数据搬迁，还在人和流程。

安全这一层两种库都要做。传输加密用 SSL/TLS，存储加密有列级加密和透明数据加密两条路，后者整库加密、读写由引擎自动加解密，对应用无感。图数据还要额外考虑隐私，差分隐私往数据里加噪，让攻击者判断不出某条边是否存在；随机响应在查询侧加噪，按概率分布返回结果。两者一个动数据，一个动答案，常常配合使用。

自测

为什么属性表答不了 Q1 这种邻居查询，明明它只要一次页读？

一次页读拿回来的是这个实体的属性，邻居是另外一批实体。属性表里实体之间的关系只体现为外键值，要拿到邻居还得去关系表里按这个外键再查一遍。省下的那一次读，被关系查询又补回去了。

三元组表的主键为什么必须是三列合起来，只用 subject 不行吗？

subject 会重复。王健林一个人就有任职于、父子、职务、出席四条边，只拿 subject 做主键，这四行会撞成一个键值。三列合起来才唯一确定一条事实。

谓词透视之后的稀疏是从哪来的，为什么不干脆不建那些空列？

稀疏来自「一类实体一张表」这个前提。同一类实体的属性集合不一致，表只能取所有属性的并集，用不上的位置填 NULL。不建空列就没有统一的表结构，也就没有一次页读取整行的便利。

二元表把空值问题彻底解决了，为什么还会被换掉？

它把稀疏换成了分散。谓词数量就是表数量，一个跨五个谓词的查询要 join 五张表，连接顺序还影响中间结果大小。谓词在知识图谱里是持续增长的那一类东西，表数量跟着涨很难维护。

穷举索引已经三个方向全建了，为什么还要复合索引？

穷举索引只覆盖头、谓词、尾三个位置，不知道实体类型。查询常常只要某一类实体，复合索引多存一列类型，范围扫描时能直接过滤掉一半的块，少读一半数据。

免索引邻接的查询时间真的和全图规模无关吗，那为什么还会有慢查询？

与全图规模无关，与局部子图有关。邻居特别多的节点，邻接链会很长，一跳也要读很多条记录。深链查询还会把每一层的邻居都乘起来，局部膨胀一样会拖慢。

内联属性和动态属性，工程上到底怎么分工？

按属性大小乘访问频率来分。名称、类型这种小且常查的放内联，一次寻址就读到；简介、图片地址这种大且少查的放动态块，节点里只留块号，多一次跳转但节点能保持定长。

同一条两跳查询，Cypher 和 SPARQL 的代价为什么差不多？

两种写法最后都展开成一次连接。Cypher 的路径模式由引擎翻译成按层展开，SPARQL 的两个模式靠共享变量接起来，物理执行都是一次邻接读取。语法糖不影响页读次数。

一个中型系统想上原生图库，三代演进里哪一代的短板最可能落到它头上？

落到第二代。单机原生读得快，但单机上限是硬约束，做主备也只能横向读不能横向写。数据量还在十亿以下时够用，再往上就得换到原生分布式，代价是跨分区的跳转变慢。

一个跑了很多年的关系库，多跳查询变慢，该不该迁到图库？

先看多跳查询占多少。占比低，加索引或做物化视图更划算；占比高且落在核心链路上，才值得评估迁移。迁移成本不只在数据，还在团队运维经验的重新积累。
