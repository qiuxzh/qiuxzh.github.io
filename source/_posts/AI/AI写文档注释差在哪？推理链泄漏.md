先看一个场景。你花了两周比较两套实现方案，评审会上大家拍板用 B。散会后你回到工位，把注释改成了这样一行：

```js
// 改用 B 方案了，A 先放放
```

你当时清楚它在说什么：A、B 是刚才会上两个有名字的方案，B 是定下来的那个。提交完，你继续做别的去了。

三个月后，接手的人翻到这行注释。B 是什么？A 又是什么？「改用」是相对哪个版本？注释只有一行，答案全不在里面。

它属于一类有名字的毛病：**推理链泄漏**。


## 什么是推理链泄漏

**文字的视角站在写它的那次会话里，而不是站在它描述的对象现在的状态上。**

它的典型表现有三种。

- 引用只有那次会话能看到的产物，比如一个方案编号，或是一次评审里的否决。
- 叙述「改了什么」，而不是「现在是什么」。
- 替自己的做法辩护，仿佛当初提出质疑的人还坐在对面。

## 为什么写的时候看不出来

三种表现说的都是结果，原因在写下它的那一刻。它迷惑人的地方在于，**写的时候完全合理**。作者手里握着全部上下文，每个缩写、编号、代词都有明确所指。几个月后读它的人，手里没有那份上下文，于是每个指代都成了断头路。

这几乎是大模型的默认行为：它生成的文字默认要接着「生成它的那段上下文」往下读得通，而交付物却需要在一段它并不拥有的上下文里独立成立。比如在对话里让模型把这次改动写成一段说明，它很容易交出这样的句子：

> 缓存粒度按前面说的改掉了，顺带处理了那个一致性问题。

「前面说的」和「那个一致性问题」在对话里都指得出来，可这行字落进一份独立文件后，就没人能找到所指。两者的视角差，就是泄漏的入口。

## 判定标准

判断一段话是不是泄漏，只需要问一个问题：

> 一个站在今天的读者，**没有会话记录，没有聊天历史，也没拿到未提交草稿**，能不能解析出每个引用、核实每个断言？

不能，就是泄漏。技术文档里的「这位读者」通常就是「当前代码，加上仓库里搜得到的东西」。

## 跨场景的例子

同一个毛病落在不同的场景里，表现并不一样。下面几例都按「写时为什么通」和「后来为什么卡」并排放在一起。

### 代码注释

你在处理输入之前补了一个判空，顺手在函数上方加了句注释：

```js
// 之前没判空，线上出过问题，补上了
```

**后来**：读者看不到当初出了什么问题，也判断不出这个判空现在还在防什么。注释记的是「一次修补」，不是这段代码的前提。

**改写**：把原因写成现在时的事实：

```js
// 必须先判空：空输入会让后续处理崩溃
```

### README / API 文档

你给某个命令的等待时间加了配置项，顺手更新了 README：

> 等待时间以前写死是 30 秒，现在可以配置了，默认值不变（PR #88）。

**后来**：读者不知道「以前」指哪一版，打不开 PR \#88，连默认值到底是多少也没读到。

**改写**：把现在的事实直接写出来：

> 等待时间默认 30 秒，可用 `--timeout` 改。

### PR 描述 / 评审回复

评审时有人建议「这个字段干脆删掉」，你解释了它还被外部依赖，在 PR 描述里写：

> 按评审意见保留了这个字段。

**后来**：读者看不到那条评审意见，也不知道这个字段为什么不能删。

**改写**：把不能删的原因写出来：

> 保留 `status` 字段：外部系统仍在读取，删掉会破坏它们的解析。

### 设计文档 / 会议纪要

一次会后，你在设计文档里追加了一句：

> 会上决定先不做离线模式，第三季度再看。

**后来**：半年后换人接手，「会上」是哪次会无从查起，「第三季度」不知是哪一年，这条待办慢慢就没人提了。

**改写**：结论留在正文，推迟的事挂到可追踪的地方：

> 当前只支持联网使用；离线模式见 issue \#1470。

### 即时消息 / 邮件

你在群里和同事敲定了列表的返回方式，随后给他发了条消息：

> 就按上次说的那个方案来吧，细节你懂的。

**后来**：消息转给了另一个人，或者三个月后自己回翻，「上次」「那个方案」全都无处可查。

**改写**：把「那个方案」展开成一句能独立读懂的话：

> 列表每批返回 20 条，并带一个字段告诉客户端还有没有下一批。

### 个人笔记

你把一段代码换个写法后，在笔记里记了一句：

> 换了个更简单的写法，快多了。

**后来**：过了半年，你只看到「更简单」「快多了」几个字；原来是什么写法、快了多少、跟什么比，笔记里一个字都没有，这个判断也就没法再复现。

**改写**：把当下的做法和理由写下来：

> 现在一次读完再处理：分批读会反复读同一个位置。

## 形态总览

前面三种表现是粗分，落到具体的文本上，常见的就是下面这几种形态。

| 形态         | 典型写法                    | 它该去哪                     |
| ---------- | ----------------------- | ------------------------ |
| 死引用        | `(决策 7)`、`§4.2`、阶段 `T4` | 指向真正归属的文件；没有主的，删代号、留事实   |
| 栈 / PR 视角  | 「本 PR 加了分页」             | 写成当前机制：「列表按游标分页」         |
| 变更叙述 / 版本戳 | 「以前是」「不再」「v1」「这次」       | 历史留在 commit、ADR；界面只写现在   |
| 评审编排       | 「评审已否决 X」               | 保留决策和理由，删掉「谁在哪个回合说的」     |
| 对评审人说话     | 「这里安全，因为……」             | 陈述让代码安全的不变量              |
| 复述推导       | 「先归一化，再截断，再换行」          | 删。代码和测试已经说明了             |
| 对冲残渣       | 「目前大概够用」                | 换成真实边界，或标成 `TODO(name):` |
| 语言滑落       | 混进未翻译的工作稿片段             | 翻译或删除                    |

**变更史 → commit / PR；理由 → 决策记录；推迟 → TODO / issue；当前行为 → 文档和注释。** 放错了地方，就成了泄漏。

## 危险之处：修复不是删除

按上面的去处动手改，最容易失手的地方恰恰是删过头。

一段泄漏文字通常是两层：外面是会过期的壳，里面是仍然成立的事实。整段删掉，事实也一起没了。下面这几种翻车都很典型。

**把义务翻转成背书。**
> 原句：这些直接注册是例外，待迁移到 slot。
> 改错：这些直接注册是被认可的例外。

「待迁移」是一种义务，被缩成「被认可」后，义务变成了背书，短了，情态却反了。

**把假设提升为已发布。**
> 原句：一个未来的 IPC shell 会继承此执行器并覆写 `spawn`。
> 改错：一个 IPC shell 继承此执行器并覆写 `spawn`。

删掉 `future` 一词，一句设计示意就变成了「此类已经存在」的断言。

**连真事实一起删。**
> 原句：这段提示文本同时是 `verify-doc-typecheck` 编译对照的对象。
> 改错：（整句删掉）

前半句是叙述，后半句是承重的耦合。命题同行时，删从句，不删句。

**留下数字却丢掉来源。**
> 原句：4 MiB 的上限是实测的，最大的生成模块是 3.1 MiB。
> 改错：上限是 4 MiB；最大的生成模块是 3.1 MiB。

少了「实测」二字，`3.1 MiB` 从一次观测读成了一个定义，再没人会在调整上限前重新测量。

**删之前，先枚举这段文字承载了哪些命题**：谁是行为者，条件是什么，发生在什么时机，情态是 must 还是 may，有没有否定保证，失败时会怎样。凡是事实从句，都要重述到能独立成立；删掉的只是包在它外面的会话痕迹。

## 反过来，这些要保留

这些形态之外，还有一类引用带着「历史感」，却并不算泄漏。下面这些能在当前上下文里解析，是合法引用，应当留下：

- `#1470` 这类 issue 引用，在任何界面都能解析，推迟的工作正该放这里。
- 已合并 PR 的引用，在决策记录、事故复盘里是被认可的变更证据。
- 抑制理由 `oxlint-disable … -- reason`，理由错了要修正，绝不能删除。
- 实测边界 `(实测：512 层嵌套约 0.15s)`，「实测」标识它是数据，不是猜测。
- 运行时的新旧：`旧连接先排空，新连接才接受`，这是生命周期，不是仓库变更史。

## 落成一条习惯

上面几条判据，落到动作上只有一句。动手写任何打算长期留存的东西之前，先问一句：

> **这段话里的每个引用，未来的读者（哪怕就是三个月后的我）在手上能查到吗？**

查不到的，要么重述成能独立成立的事实，要么删掉。这个动作要多花一点注意力，但它换来的是：任何人在任何时间点打开这段文字，都不需要重建你的思考现场，就能读懂它。
