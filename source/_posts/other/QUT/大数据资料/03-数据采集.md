> 一条数据从产生到能算出结论，中间隔了几道工序？

① 采集Acquisition → ② 存储Storage → ③ 清洗Cleaning → ④ 挖掘Mining → ⑤ 可视化Visualization

采集排在第一道。它是大数据处理的**第一步**，数据是后续所有处理的基础，而采集到的数据完整不完整、质量好不好，**直接决定后面每个环节的结果**。

> 采集不就是把文件拷过来吗？

比拷文件麻烦得多。数据散在关系型数据库、平面文件、日志、网页里，格式各不相同，这类来源叫**异构数据源**（*heterogeneous data sources*）。要让它们能放到一起算，中间得先过一段管道，这段管道叫 **ETL**。

三个字母分别是**抽取**（*extract*）、**转换**（*transform*）、**装载**（*load*）。做法是：从异构数据源把数据抽到临时的中间层，在那里清洗、转换、集成，最后装进**数据仓库**（*data warehouse*）或**数据集市**（*data mart*），形成一个统一的数据视图（*unified data view*），供后续查询和分析。

异构数据源sources → 临时中间层staging → 清洗 / 转换 / 集成 → 数据仓库 · 数据集市

> **E 只是采集，采集不止于 E**
>
> 抽取是采集，但后面清洗、转换、集成都属于「把数据变得能用」的工序，习惯上一起挂在 ETL 这个名字下面。分开记更清楚：**采集负责把数据弄进来，ETL 负责把数据弄整齐。**

### 数据从哪来：批量源与实时源

数据源的类型很杂，结构化、半结构化、非结构化都会出现，量可能很大也可能很小，还可能是持续不断的流式数据。按「什么时候到」分成两类更好抓重点。

| 类别 | 典型来源 | 对采集的要求 |
| --- | --- | --- |
| **批量数据源**<br>*batch* | 文件、日志、关系型数据库 | 攒一批再搬，看重吞吐；晚几分钟没关系 |
| **实时数据源**<br>*real-time* | 机器产生的传感器数据、物联网系统实时上传的数据、社交媒体数据、股票行情 | 速度高，需要**低开销、低等待**的通信机制 |

新一代的数据分类体系把新数据源另分了两大类，这两种在后面的日志与行为分析里反复出现。

| 类别 | 包含什么 |
| --- | --- |
| **线上行为数据** | 页面数据、交互数据、表单数据、会话数据 |
| **内容数据** | 应用日志、电子文档、机器数据、语音数据、社交媒体数据 |

### 传统采集与大数据采集差在哪

两者是两回事，四个维度都不在一个量级。

| 维度 | 传统数据采集 | 大数据采集 |
| --- | --- | --- |
| 数据源 | 单一来源，数据量相当小 | 来源广泛，数量巨大 |
| 数据类型 | 结构单一 | 类型丰富 |
| 承载系统 | 关系型数据库、并行数据库 | 分布式数据库 |
| 工具 | 一套工具可以完成采集与集成 | **不可能靠单一工具或技术完成** |

最后一行是关键。**大数据采集是一组工具的组合，不是一个产品。** 后面讲的四条路线，就是为了对付四种形态完全不同的数据源。

> **采集的位置**
>
> ① 采集是第一步，数据的**完整性与质量**决定后面所有结果；<br> ② 异构数据源到数据仓库之间要过 **ETL** 这段管道，E 只是其中一段；<br> ③ 大数据采集**没有单一工具**，路线取决于数据源长什么样。

> **总结**
> 1. **位置**：采集 → 存储 → 清洗 → 挖掘 → 可视化，采集是第一步。
> 2. **ETL**：抽取、转换、装载；异构源 → 临时中间层 → 清洗/转换/集成 → 数据仓库或数据集市。
> 3. **数据源**：批量源（文件、日志、关系库）与实时源（传感器、物联网、社交、行情）。
> 4. **新分类**：线上行为数据（页面、交互、表单、会话）与内容数据（应用日志、电子文档、机器数据、语音、社交媒体）。
> 5. **差别**：来源更广、类型更杂、承载换成分布式库、工具无法单一化。

## 3.2　四条采集路线

> 传感器、数据库、服务器日志、网页，这四类数据是用同一套办法收上来的吗？

不是。来源不同，接法完全不同。采集场景分四类：**传感设备**（sensing device）、**数据库采集系统**（database）、**系统日志采集系统**（system log）、**网络数据采集系统**（network）。

### 传感设备：有线与无线

传感网分两种：**有线传感器网络**（*wired sensor network*）和 **无线传感器网络**（*wireless sensor network*，WSN）。前者靠线连，后者靠无线自组网，部署成本差很多，采集的数据形态却一样：单个读数很小，来得又密。

可穿戴设备是最贴近生活的例子。一个智能手环内部是这样搭的：一颗 **MCU** 或处理器（内置或另外配小容量 RAM、ROM）负责控制蓝牙、传感器、LED 和振动器，纽扣电池或锂电池供电。手环界的鼻祖是 Fitbit Flex。

这类采集的共同点是**数据自动产生、持续不断、单条极小、总量很大**，所以它天然适合流式处理，而不是攒成文件再传。

### 数据库采集：把库本身当数据源

传统企业把业务数据放在 MySQL、Oracle 这类关系型数据库里。到了大数据时代，HBase、Redis、MongoDB 这类 NoSQL 库也成了常见的采集对象。

采集端的做法是**部署大量数据库**，在库之间做**负载均衡**（*load balancing*）和 **分片**（*sharding*），把写入和查询压力摊到多台机器上。数据在关系库与外部系统之间搬移，常用的转换工具是 **Sqoop**。

### 系统日志：一条日志一次行为

日志里记的东西分四类：**行为**（behavior）、**交互**（interactions）、**状态**（status）和**系统日志**（system logs）。

**Web 日志**是前端各台 Web 服务器产生的访问日志，加上各种 Web 应用输出的日志。在 Web 日志里，**每条日志通常代表用户的一次访问行为**，所以它既是技术记录，也是行为数据。

一条日志能拆出十个字段，每个字段单独看都是一个小指标。

| # | 字段 | 记的是什么，能拿来干什么 |
| --- | --- | --- |
| 1 | 远程主机 IP 地址 | 访问者的 IP，可用于判断地理位置与网络状况 |
| 2 | 用户代理 *user-agent* | 浏览器的类型与版本，用于了解设备与技术 |
| 3 | 请求方法 | GET、POST 等，反映交互方式 |
| 4 | 请求路径 | 访问的页面或资源路径，用于分析浏览路径与兴趣 |
| 5 | 请求协议 | HTTP、HTTPS |
| 6 | 响应状态码 | 200 成功、404 找不到页面 |
| 7 | 响应长度 | 响应文件的大小，用于估计下载量与数据量 |
| 8 | 访问时间 | 事件发生的时间，用于找活跃时段与访问高峰 |
| 9 | 用户标识 | 用户名、Cookie 等，用于区分身份 |
| 10 | 请求头与请求参数 | 请求头信息与传递的参数，用于推测操作意图 |

大公司的平台每天都在产生海量日志，而且这些日志通常是**数据流**，比如搜索引擎的 pv 和查询词。处理它们需要专门的日志采集系统，任务是把日志收起来，同时提供离线和在线实时两种分析能力。

这类系统的硬性要求有三条：采用**分布式架构**，能满足每秒数百 MB 的日志采集与传输；具备**高可用**（*high availability*）；具备**高可靠**与**可扩展**（*scalability*）。

| 工具 | 出处 / 特点 |
| --- | --- |
| **Apache Chukwa** | 建立在 Hadoop 之上的日志采集与监控系统 |
| **Apache Flume** | 海量日志采集、聚合、传输的分布式系统 |
| **Facebook Scribe** | Facebook 开源的日志收集框架 |
| **LinkedIn Kafka** | 高吞吐的分布式消息队列，常做日志的缓冲与分发 |

> **pv 是什么**
>
> *page views*，页面访问量。同一个用户刷新三次，记三次。要和「访客数」区分开，后者按人去重。

### 网络采集：爬虫与 API

两条路：写**爬虫**（*web crawler*）从网页上抓，或者调网站开放的 **API** 拿结构化数据。

爬虫是按一定规则、**自动**抓取网页信息的程序或脚本，能把它访问得到的页面内容全部自动收下来。它替搜索引擎从万维网上下载网页，所以是搜索引擎的重要组成部分。

爬虫的用途分两类，目的完全相反。

| 类型 | 典型用途 | 看重的指标 |
| --- | --- | --- |
| **搜集型**<br>*collection* | 互联网搜索引擎、网络舆情收集、学术论文采集、离线浏览器 | 全面性与数据量，恨不得把能碰到的都收下来 |
| **监控型**<br>*monitoring* | 网页挂马监测、SQL 注入攻击检测、社交媒体评论监测、敏感信息、泄露信息 | 时效性与变化，只盯特定站点改动 |

> **四条路线的分野**
>
> 传感器靠**设备自动产生**；数据库靠**库间复制、分片与均衡**；日志靠**专门的分布式采集系统**；网页靠**爬虫或 API**。选哪条，看数据原本待在哪里。

> **总结**
> 1. **四类场景**：传感设备、数据库采集、系统日志采集、网络数据采集。
> 2. **传感器**：有线 / 无线传感器网络；手环 = MCU + 小容量 RAM/ROM + 蓝牙 + 传感器 + 电源。
> 3. **数据库**：传统 MySQL / Oracle，大数据时代加 HBase、Redis、MongoDB；靠负载均衡与分片摊压力；搬运用 Sqoop。
> 4. **日志**：记行为、交互、状态、系统日志；一条 Web 日志 = 一次访问行为，可拆十个字段；系统要求分布式、每秒数百 MB、高可用、可扩展；工具有 Chukwa、Flume、Scribe、Kafka。
> 5. **网络**：爬虫或 API；分搜集型与监控型，前者看全面性，后者看时效性。

## 3.3　爬虫的四层结构

> 一个爬虫程序，拆开看由哪几层组成？

| 层 | 负责什么 | 对应的现实动作 |
| --- | --- | --- |
| **网络连接层**<br>*network connection* | 建立 TCP Socket 连接、传输数据、管理连接 | 跟服务器握手，把请求送出去 |
| **页面采集层**<br>*page acquisition* | 处理 URL、提取域名，在任务多时按搜索策略决定抓取顺序 | 从待办清单里挑下一个地址 |
| **页面抽取层**<br>*page extraction* | 从 HTML 文本里抽出超链接和正文 | 把有用的字段抠出来 |
| **领域处理层**<br>*domain processing* | 某类爬虫才需要完成的功能，如主题爬虫、Deep Web 爬虫 | 普通爬虫用不到这一层 |

四层里前三层是通用骨架，第四层是给专门用途留的口子。拆分的好处是每一层都能单独换：换连接库不影响抽取，换解析库不影响调度。

*四层竖着摞，最底下一格是 Web 服务器。右侧箭头是数据的走向：从字节流到 HTML，再往上才是能存进表的字段。*

### 连接层：先得说上话

连接层由 **Web Server 连接器**（connector）向指定的 Web 服务器发起连接请求，连上之后这条连接就是后续发送 URL、接收服务器消息的通道，一直用到爬虫或服务器主动断开。

抓取过程中可能要反复重连。为了减少「域名转换 IP」的时间，爬虫通常要支持 **DNS 缓存优化**（*DNS cache*）。

> **DNS 在做什么**
>
> *Domain Name System*，把域名解析成 IP 地址。缓存就是把这层对应关系存在本地，下一次直接查表，不再问一遍。

### 采集层：决定先抓谁

拿到 HTML 之后，页面解析器（parser）先把里面包含的 URL 抽出来，再按两条规则过滤：**robots.txt 的访问许可列表**、**这个 URL 是否已经抓过**。过滤完的地址按某种爬取策略放进资源地址列表，也就是 **URL 池**（*URL pool*），有时候也叫种子（*seed*）。

然后连接器从池里取下一个 URL，抓完再取，循环到抓取任务为空或被人中断。

这个循环说明了一件事：**URL 池既是待办清单，也是这套系统的瓶颈所在**。池子会涨，是因为每个页面都能贡献新的链接；池子会空，是因为链接被过滤或被限速。

### 抽取层：把正文抠出来

抽取层干两件事：抽出页面里的**超链接**（给下一轮当种子），抽出**网页内容**（这才是最终要的数据）。前者决定爬虫能走多远，后者决定爬虫有没有用。

### 用 requests 打通连接层

*requests* 是 Python 里处理网络连接、请求与响应的库，能把 Web Server 连接器的开发量压到很低。

| 函数 | 作用 |
| --- | --- |
| `requests.request()` | 构造一个请求 |
| `requests.get()` | 获取 HTML 网页的主要方法，对应 HTTP 的 GET |
| `requests.head()` | 获取网页头部信息，对应 HEAD |
| `requests.post()` | 提交 POST 请求 |
| `requests.put()` | 提交 PUT 请求 |
| `requests.patch()` | 提交局部修改请求，对应 PATCH |
| `requests.delete()` | 提交删除请求，对应 DELETE |
| `requests.Session()` | 在不同次请求之间保持某些参数 |

一次访问在协议上是两段：客户端先发**请求**（request），服务器验证请求有效性后返回**响应**（response），客户端再把内容展示出来。

```python
import requests

url = "http://www.baidu.com"
strhtml = requests.get(url)
print(strhtml.text)
```

默认请求里没有浏览器的标识。想模拟成任意浏览器，加一个 `headers` 字典就行。

```python
http_headers = {'User-Agent': 'Mozilla/5.0'}
r = requests.get("url", headers=http_headers)
```

⚠️ 不加 `headers`，请求里就不带 *user-agent*，服务器一眼能看出这是脚本在访问。这正是反爬措施里最基础的一条，检测点就在请求头上。

### 编码：乱码从哪来

**网页编码**（*web page encoding*）指网页里字符的编码方式。国内常见三种：utf-8、gbk、gb2312。其中 **utf-8**（*8-bit Unicode Transformation Format*）是国际编码，各国各地区的网站都常见，可以说是最通用的字符编码。

Python 3 的字符串默认按 **unicode** 存储，所以 gbk、gb2312、utf-8 之间的转换都要经过 unicode 中转。`encode()` 把 unicode 编成字节序列，`decode()` 把字节序列解回 unicode。

```python
n = '大数据'                            # unicode
g = n.encode('gbk')                     # → gbk 字节
u = n.encode('utf-8')                   # → utf-8 字节
g2 = n.encode('gb2312')                 # → gb2312 字节

g2u = g.decode('gbk').encode('utf-8')   # gbk 转 utf-8：先解码回 unicode，再编码
```

判断一个页面用什么编码，看它的 *charset* 属性。声明成这样就是 utf-8：

```html
<meta charset="utf-8">
```

用错编码去解析，拿到的就是乱码。这个坑在解析那一层最容易撞上，因为错误不会报异常，只会静静地给出错字。

> **三层，外带一道编码**
>
> ① 爬虫分**连接、采集、抽取**三层，第四层只给特定用途；<br> ② 连接层靠 `requests` 加 `headers`，采集层靠 URL 池调度顺序；<br> ③ 编码要过 unicode 中转，**解码用错编码不会报错，只会出乱码**。

> **总结**
> 1. **四层**：网络连接层（TCP Socket、传输、连接管理）、页面采集层（URL 处理、域名提取、抓取顺序）、页面抽取层（超链接与正文）、领域处理层（主题爬虫、Deep Web 爬虫才需要）。
> 2. **采集层循环**：解析出 URL → 按 robots 许可与是否抓过去重 → 入 URL 池（种子）→ 取下一个 → 循环到任务为空。
> 3. **requests**：get / head / post / put / patch / delete / Session；加 `headers` 伪装 *user-agent*。
> 4. **编码**：utf-8 通用，gbk、gb2312 国内常见；Python 3 字符串是 unicode，转换靠 encode / decode，中间必须过 unicode。

## 3.4　Robots 协议

> 网站不欢迎爬虫，它用什么方式告诉你？

暴力爬虫会给网站服务器带来很大压力，所以各类站点都对爬虫设了限制，这叫**反爬**（*anti-crawler*）。最基础的一层限制是 **Robots 协议**。

它的全名是 **Robots Exclusion Protocol**（REP），也叫爬虫协议。网站通过它告诉搜索引擎 **哪些页面可以抓、哪些不能抓**。文件默认放在站点根目录，文件名 `robots.txt`。一个站点如果压根没有这个文件，默认允许所有爬虫访问它的内容。

```robots.txt
User-agent: *
Disallow: /admin/
Allow: /public/
Crawl-delay: 2
```

三行的意思：对所有爬虫生效、不要抓 `/admin/`、允许抓 `/public/`、两次抓取之间至少隔 2 秒。`User-agent` 是 HTTP 头部字段，用来标识发起请求的客户端类型与版本，写具体名字就是对那一类爬虫单独生效，写 `*` 就是对所有爬虫生效。

### 爬虫读这个文件的六个步骤

1. 检查虚拟根目录下有没有 `robots.txt`；
2. 如果服务器返回 404，说明文件不存在，直接跳到第 6 步；
3. 文件存在，把它读回本地；
4. 逐条解析记录。爬虫的 User-agent 出现在某条记录里，就读那条记录里的 Disallow 或 Allow 部分；遇到不认识的 User-agent，就去找以 `User-agent: *` 开头的那条记录，读它的 Disallow 或 Allow；
5. 根据抽出来的 Disallow / Allow 建立访问许可列表；
6. 结束。

注意第 4 步的两个分支：**认得自己就读自己那条，认不得就读通配那条**。这是整段流程里唯一需要判断的地方，也是写解析器最容易漏的地方。

### 在 Python 里读它

标准库自带 `RobotFileParser` 类，不用自己写解析。

| 方法 | 作用 |
| --- | --- |
| `set_url(url)` | 设置指向 robots.txt 的 URL |
| `read()` | 读取 robots.txt |
| `can_fetch(useragent, url)` | 判断该 useragent 能否访问该 url，`True` 可访问、`False` 不允许 |
| `crawl_delay(useragent)` | 返回抓取延时；文件里没给这个 useragent 指定延时，返回 `None` |
| `request_rate(useragent)` | 返回抓取频率；没指定则返回 `None` |

```python
from urllib.robotparser import RobotFileParser

rp = RobotFileParser()
rp.set_url("https://example.com/robots.txt")
rp.read()

print(rp.can_fetch("MyBot", "https://example.com/admin/"))   # False
print(rp.can_fetch("MyBot", "https://example.com/public/"))  # True
print(rp.crawl_delay("MyBot"))                                # 2，或 None
```

⚠️ 没有 `robots.txt` 不等于不受限制。协议之外还有技术手段：识别非浏览器访问、封 IP、弹验证码、封账号，这些在 3.7 末尾一起讲。

> **总结**
> 1. **名字**：Robots Exclusion Protocol，放在站点根目录的 `robots.txt`；没有该文件默认全部允许。
> 2. **语法**：`User-agent` 指定对谁生效，`Disallow` / `Allow` 指定路径，`Crawl-delay` 指定间隔。
> 3. **判读**：找文件 → 404 就结束 → 读回 → 按自己或通配记录取规则 → 建许可列表 → 结束。
> 4. **Python**：`RobotFileParser` 的 set_url、read、can_fetch、crawl_delay、request_rate。

## 3.5　爬取顺序：DFS、BFS 与 PageRank

> 待抓的 URL 有几亿条，先抓哪一条？

**爬取策略**（*crawling strategy*）指把每个页面解析出来的超链接排出一个抓取顺序，本质是排序问题。设计这个顺序要守两条限制：

1. 不要给 Web 服务器太大压力；
2. 不要占满客户端自己的资源。

第二条容易被忽略。每条连接都消耗本机的网络与算力，线程开太多、长连接留太多、超时参数设得不合适，先撑不住的往往是客户端自己。

### 把互联网看成一个有向图

把网页建模成图之后，「先抓哪个」就变成了「这个图怎么遍历」。理论上按遍历算法走一遍，几乎能访问到互联网上所有网页。

两种都走极端：一条道走到黑会陷进深链接出不来，铺开走会把 URL 池撑爆。所以难点是**用什么顺序排优先级**。

### PageRank：给页面排出重要性

抓取的起点通常选比较重要的页面。确定下一个抓谁时，总希望高优先级的先抓。在大规模分布式环境里，各台机器性能不一样，设计者希望把重要页面的抓取分配给它性能好的机器，靠这个提升整体性能。于是需要一个能**量化页面重要性**的办法。

**PageRank** 就是这个经典算法。它出自 Google 搜索引擎，思路是用网页之间的相互超链接计算页面排名，由 Larry Page 和 Sergey Brin 在 1990 年代后期提出。因为它解决的是「网络图里每个节点有多重要」这个问题，凡是可以抽象成网络连接图的应用，都能搬过去用。

### 两个假设

| 假设 | 内容 |
| --- | --- |
| **数量假设**<br>*quantity* | 一个页面收到的入链越多，这个页面越重要 |
| **质量假设**<br>*quality* | 指向某个页面的入链质量不同，高质量页面会通过链接传出更多权重；指向它的页面越重要，它就越重要 |

还有一条分配规则：**一个页面的重要性，平均分给它指向的每一个页面。**

*四条规则摊成一张表：行是把糖给出去的人，列是收到糖的人。C 行第 C 列有值，说明 C 把一半留给了自己，方程里 p(C) 右边因此多出一项 p(C)。*

```text
p(A) = 1/3 · p(D)
p(B) = 1/2 · p(A) + 1/3 · p(D)
p(C) = 1/2 · p(A) + 1/2 · p(C) + 1/3 · p(D)
p(D) = p(B) + 1/2 · p(C)
p(A) + p(B) + p(C) + p(D) = 1
```

这组方程构成一个**马尔可夫链**（*Markov chain*）。四人之间的分配关系可以写成一个矩阵，就是**转移矩阵**（*transfer matrix*），也叫邻接矩阵（*adjacency matrix*）。

把四条等式和「总数等于 1」一起解，得到比例 **p(A) : p(B) : p(C) : p(D) = 2 : 3 : 6 : 6**。归一化之后 p(C) 与 p(D) 各占 6/17，约 0.353；p(B) 是 3/17，约 0.176；p(A) 是 2/17，约 0.118。

这个链条有两个性质。第一，**分配会收敛**：无论经过多少轮重新分配，比例都稳定到这组值。第二，**收敛值与初始值无关**：谁一开始手里糖多、谁少，最后都停在同一组比例上。后面这一点，正是 PageRank 能给出唯一排名的基础。

### 推广到网页

把「人」换成「页面」，把「给糖」换成「给出链」。对一个页面 u，指向它的所有页面构成集合 B(u)，它的重要性 PR 值等于每个入链页面把自己的 PR 值平均分给它的份额之和：

```text
PR(u) = Σ  PR(v) / L(v)          v ∈ B(u)
```

其中 L(v) 是页面 v 的出链数量。这一行就是「把重要性平均分给出链」的数学写法，也就是糖果模型里「平均分」三个字的正式版本。

> **顺序问题的三个层次**
>
> ① 能遍历：DFS、BFS 都是图的遍历；<br> ② 会踩坑：DFS 不收敛、BFS 撑爆 URL 池，两个方向各有各的病；<br> ③ 要排序：PageRank 用**入链数量**加**入链质量**给页面打分。

> **总结**
> 1. **爬取策略**即抓取顺序；两条限制：不给服务器加压、不占满本机资源。
> 2. **图模型**：网页是节点，链接是有向边，抓取顺序就是遍历顺序。
> 3. **DFS** 顺序 A-B-F-I-C-D-G-H-J-E，容易不收敛、无限抓取；**BFS** 顺序 A-B-C-D-E-F-G-H-I-J，减轻服务器压力但 URL 池易溢出。
> 4. **PageRank**：数量假设 + 质量假设，加权平均分配；糖果模型解出 2:3:6:6；公式 PR(u) = Σ PR(v)/L(v)。
> 5. **马尔可夫链性质**：收敛，且收敛值与初始值无关。

## 3.6　网页怎么读：DOM、BeautifulSoup 与正则

> 抓回来一大坨 HTML，怎么把标题、价格、评论数这几个字段挑出来？

先分清网页的三部分：**HTML** 决定结构和内容，**CSS** 决定样式，**JavaScript** 控制行为。一个网站通常由多个网页组成，一个网页就是这三样拼起来的，可以记成**骨架、皮肤、肌肉**。

| 类型 | 特征 | 常见后缀 |
| --- | --- | --- |
| **静态网页**<br>*static* | 没有后台数据库，不交互 | `.htm`、`.html`、`.xml` |
| **动态网页**<br>*dynamic* | 能与后台数据库交换数据，可交互 | `.asp`、`.aspx`、`.jsp`、`.php` |

网页本质上是**超文本**（*hypertext*），上面的所有内容都放在 `<>...</>` 这样的标签里。每个 HTML 文档有一个整体结构，分**头部**（head）和**主体**（body）：头部描述浏览器需要的信息，主体包含网页要展示的具体内容。

```html
<!DOCTYPE html>
<html>
<head>
  <meta charset="utf-8">
  <title>标题</title>
</head>
<body>
  <h1>页面</h1>
  <p>内容</p>
</body>
</html>
```

### 标签树就是 DOM

网页有固定的结构，由 HTML 标签组成一棵树。这棵标签树叫 **DOM 树**（*Document Object Model*），DOM 提供一种**面向对象**的方式去描述文档。

抽取就利用这棵树，分三步：把网页文档解析成 DOM 树；判断要抽取的内容在哪个节点上 （节点名和属性是唯一的）；用各种方法定位到该节点，把节点里的内容取出来。

**XPath** 是描述「从节点 A 到节点 B 的路径」的表达式，例如：

```xpath
/html/body/div[4]/div[2]/div/div/ul/li[1]/a
```

基于 HTML 结构做抽取的开源库已经很多，它们替你建好 DOM 树，再提供丰富的搜索策略：`html.parser`、`lxml`、`html5lib`、**BeautifulSoup**、`PyQuery`。XPath 属于 `lxml` 模块，用之前要先装 `lxml`。

### BeautifulSoup：只管定位，不管解析

BeautifulSoup 自身没有解析文档的代码，它依赖别的解释器，可以看成对其他解释器的**再封装**，最后给使用者一个统一的编程接口。默认用标准库的 `html.parser`，因为要调用别的开源库，运行效率相对偏低，但编程方式简单。

```bash
pip install beautifulsoup4
```

```python
import requests
from bs4 import BeautifulSoup

wb_data = requests.get(url, headers=headers)
soup = BeautifulSoup(wb_data, 'lxml')
```

| 解析器 | 用法 | 前提 |
| --- | --- | --- |
| bs4 的 HTML 解析器 | `BeautifulSoup(r,'html.parser')` | 装 bs4 库 |
| lxml 的 HTML 解析器 | `BeautifulSoup(r,'lxml')` | `pip install lxml` |
| lxml 的 XML 解析器 | `BeautifulSoup(r,'xml')` | `pip install lxml` |
| html5lib 的解析器 | `BeautifulSoup(r,'html5lib')` | `pip install html5lib` |

> **bs4 是包，BeautifulSoup 是类**
>
> `bs4` 这个包里还有 EntitySubstitution、builder、AnnouncingParser 等类。BeautifulSoup 只是其中最常用的一个，两者不是一回事。

BeautifulSoup 把 HTML 文档转成一棵树，处理的对象只有四类：**Tag**、**NavigableString**、**BeautifulSoup**、**Comment**。

### 标签与属性

标签通常由两个尖括号包起来，成对出现时分成**起始标签**（open label）和**结束标签**（closed label）。单个标签写成 `<标签名 />`，比如 `<br />`、`<hr />`，这类叫**空元素**。

标签可以带属性，属性写在起始标签里，形式是 `名字="值"`：

```html
<标签 属性类别="属性值">标签内容</标签>

<a href="http://www.douban.com">豆瓣</a>
```

属性值应当始终加引号，双引号最常用；值里本身含双引号时改用单引号。W3C 在 HTML 4 里推荐小写，XHTML 强制小写。

⚠️ 现实中的网页并不规范：结束标签漏写、标签大小写混用、结构残缺都很常见。所以才需要解析器先把结构补全，而不是拿字符串硬切。

### 四种搜索方式

最常用的是 `find_all()` 和 `find()`：前者返回所有匹配元素组成的列表，后者返回第一个匹配的元素。所有 find 类方法的参数定义相同。

```python
find_all(name, attrs, recursive, string, **kwargs)
```

| 按什么搜 | 写法 |
| --- | --- |
| 标签名 | `soup.find_all('a')` |
| 标签属性 | `soup.find_all('a', href=...)` |
| 标签里的内容 | `soup.find_all(string='关键词')` |
| CSS 类名 | `soup.find_all('a', class_='main review')` |

取属性用 `get()`，取文字用 `get_text()` 或 `.text`：

```html
<div data-cid="123568">
  <a class="main review">78945</a>
</div>
```

```python
cid = soup.find('div').get('data-cid')                       # '123568'
rev = soup.find('a', class_='main review').get_text()        # '78945'
```

另外几个属性也常用：`Tag.name` 取标签名，`Tag.attrs` 取全部属性，`.string` 取标签里的文字，`.contents` 取全部内容。

### select：直接写 CSS 选择器

| 选择器 | 写法 | 含义 |
| --- | --- | --- |
| 标签名 | `soup.select('title')` | 所有 title 标签 |
| 类名 | `soup.select('.list')` | class 含 list 的节点 |
| id 名 | `soup.select('#link1')` | id 为 link1 的节点 |
| 直接子标签 | `soup.select('head > title')` | `>` 前后要加空格 |

类名本身带空格时，用点把每段连起来。比如 `<div class="zwli clearfix">`，写成 `soup.select('div.zwli.clearfix')`。`soup.select('.list > #link1')` 取的是类名 list 的节点下面、id 为 link1 的子节点。

`select` 返回的是 list，用下标加 `text` 取内容，比如 `soup.select('title')[0].text` 取到页面标题。

### 正则：当结构帮不上忙

**正则表达式**（*regular expression*）是对字符串操作的一种逻辑公式，用一条短式子表达对字符串的过滤逻辑，可以代表所有「有特征」或「难以描述」的字符串。Python 里由 `re` 模块提供匹配功能，主要功能是匹配、搜索、分割、替换，最常用的是 `findall`。

```python
findall(pattern, string[, flags])
```

`pattern` 是匹配模式，`string` 是输入字符串，`flags` 是可选参数，函数返回结果列表。

| 符号 | 含义 | 例子 |
| --- | --- | --- |
| `.` | 任意一个字符，`\n` 除外 | `'m...e'` 匹配 mouse |
| `*` | 前一个字符重复任意多次，含 0 次 | `'ca*t'` 匹配 caaaaat |
| `?` | 前一个字符重复 0 次或 1 次 | `'ca?t'` 匹配 cat，不匹配 caaaaat |
| `{}` | 指定重复次数或次数范围 | `'ca{5}t'`、`'ca{1,5}t'` |
| `^` | 从字符串起始位置开始匹配 | `'^m...e'` 只在开头匹配 |
| `[]` | 字符范围 | `'[0-9]{1,5}'` 取出 12 和 6 |
| `\d` | 匹配数字，等价于 `[0-9]` | `re.findall('\d','电话:10086')` 得到 5 个字符 |

```python
ret = re.findall('m...e', "cat and mouse")             # ['mouse']
ret = re.findall('ca*t', "caaaaat and mouse")          # ['caaaaat']
ret = re.findall('ca?t', "cat and mouse")              # ['cat']
ret = re.findall('ca?t', "caaaaat and mouse")          # []（无匹配）
ret = re.findall('ca{5}t', "caaaaat and mouse")        # ['caaaaat']
ret = re.findall('ca{1,5}t', "caaaat catd mouse")      # ['caaaat', 'cat']
ret = re.findall('[0-9]{1,5}', "12 cats and 6 mice")   # ['12', '6']
ret = re.findall('^m...e', "caaaat catd mouse")        # []（不是开头）
```

抽链接时可以把正则编译好再交给 `find_all`，这样它按模式而不是按标签名匹配：

```python
pattern = r"http://[a-zA-Z0-9/\.\-]*"
hrefs = soup.find_all(re.compile(pattern))
```

同样的一批链接，直接用 `re.findall` 也能拿出来，返回的是一个字符串列表，区别是少了标签结构的信息。

### 什么时候用哪个

| 情况 | 选什么 |
| --- | --- |
| 结构规整，有稳定的 id 或 class | BS4 的 `select`，最短也最稳 |
| 标签残缺、结构乱 | 先让 `lxml` 把结构修好再抽 |
| 要抓的是 URL、电话、编号这类有固定模式的东西 | 正则 |
| 只要一处文本，位置固定 | XPath |

> **谁负责定位，谁负责兜底**
>
> ① DOM 树是网页的**骨架**，抽取就是在这棵树上定位；<br> ② BS4 负责定位（find、find_all、select），属性用 `get`，文字用 `get_text`；<br> ③ 结构救不了的地方交给正则，`findall` 一个函数就够用。

> **总结**
> 1. **网页组成**：HTML 结构、CSS 样式、JS 行为；静态页不连后台库，动态页与后台交换数据。
> 2. **抽取三步**：解析成 DOM 树 → 定位唯一节点 → 取内容；XPath 表达节点路径。
> 3. **解析器**：html.parser（bs4 自带）、lxml、html5lib、xml；用哪个决定装哪个包。
> 4. **搜索**：find / find_all 按标签名、属性、文字、类名搜；select 写 CSS 选择器；取属性用 get，取文字用 get_text 或 .text。
> 5. **正则**：`.`、`*`、`?`、`{}`、`^`、`[]`、`\d`；findall 返回列表。

## 3.7　边界：框架、法律与反爬

> 技术上抓得到，是不是就等于可以抓？

不是。这一节讲三件事：用什么框架把爬虫工程化、法律边界在哪里、网站会怎么拦住你。

### 框架：从脚本到工程

手写爬虫写到一定规模，调度、去重、重试、存储都要自己搭。这一层的代表是 **Scrapy** 框架。

另一条路是直接用现成的开源包。高度封装的好处是快，代价是**很少有人愿意深究其中的关键技术**，这条路产出的爬虫在质量、性能、友好度上都受影响。小而零散的爬虫常见两个毛病：不遵守 Robots 协议，没有优化过的抓取策略。

### 法律边界：三把尺子

| 维度 | 要回答的问题 |
| --- | --- |
| **抓取权限** | 数据是否公开？页面是否授权？只面向特定人群的数据属于未公开数据；robots 协议怎么说 |
| **访问方式** | 是否影响服务器正常运行？抓取延时、抓取时段是否按 robots 协议里的约定来 |
| **数据量与用途** | 是否用于商业用途？是否涉及版权限制？是否存储并基于累积数据挖掘个人隐私 |

「公开」这件事本身也不好界定，公开是有范围含义的。

相关的法规有这些：

- 《中华人民共和国刑法》第二百八十五条，非法获取计算机信息系统数据罪；
- 《中华人民共和国网络安全法》；
- 《计算机信息系统安全保护条例》；
- 《个人信息安全规范》；
- 《数据安全管理办法（征求意见稿）》；
- 《反不正当竞争法》。

刑法 285 条说的情形是：采用破解密码、盗取密码、强行突破安全工具等手段，在没有得到许可、违背计算机信息系统控制人或所有人意愿的情况下，进入自己无权进入的计算机信息系统。

结论是，抓取互联网公开资源不违法，爬虫作为互联网大数据采集的技术手段是中性的。**越过边界的是三种叠加**：未经许可、未经授权抓取数据；导致服务器正常运行受影响；把抓来的数据用于商业用途或未经授权公开。

> **设计之前先读规定**
>
> 在设计和实现采集与挖掘系统之前，先把相关规范与法律条文读一遍。**合规与采集性能要放在一起权衡**，不能为了提高采集性能把合规丢掉。

### 反爬的四种常见手段

| 手段 | 做法 |
| --- | --- |
| **识别非浏览器访问** | 看请求头里有没有 *user-agent*，没有就拦 |
| **封 IP** | 同一个 IP 访问过于频繁就封禁 |
| **弹验证码** | 要求通过人工可解、脚本不易解的验证 |
| **封账号** | 账号行为异常时封停 |

这四条正好压在前两节讲过的两个卡点上：**连接层必须带 headers**，**采集层必须控制频率**。前面那两处是绕不开的关口。

> **框架、法律、反爬**
>
> ① 框架解决的是工程问题，不是合规问题；<br> ② 法律看三条：**有没有权限、怎么访问、拿去干什么**；<br> ③ 反爬的四招都压在连接层与采集层，绕过去才算真的抓得到。

> **总结**
> 1. **框架**：Scrapy；高度封装的开源包省事，但产物质量、性能、友好度都可能打折。
> 2. **法律三问**：数据是否公开、是否影响服务器、是否商用或涉隐私。
> 3. **中性判断**：抓公开资源不违法；越界靠三件事叠加认定。
> 4. **反爬四招**：识别非浏览器访问、封 IP、弹验证码、封账号。
