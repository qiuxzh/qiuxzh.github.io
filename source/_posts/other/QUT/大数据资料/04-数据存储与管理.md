> 一台机器装 4 TB 硬盘，要存 100 TB 数据，怎么办？

三条路：买更贵的机器、加更多便宜的机器、或者干脆不存。大数据技术选的是第二条，并且顺手改掉了一个老习惯：**不再删数据**。

### 大数据技术的三层

| 层 | 做什么 | 拿到的结果 |
| --- | --- | --- |
| **数据存储**<br>*storage* | 不再丢弃数据，**只追加、不删除** | 全量留底，历史可回溯 |
| **数据计算**<br>*calculation* | 靠分布式计算加速任务 | 过去要一天的任务，一小时内完成 |
| **数据挖掘**<br>*mining* | 发现超越常识、联系很强的关系；发现超越常规思维的规律与事件运行的实质 | 从数据走到判断 |

### 分布式系统的定义

> A distributed system consists of a collection of **cheap and ordinary computers**, connected through a network and distribution middleware to accomplish collective tasks that are impossible for a single computer.

> A distributed system is a collection of **independent computers that appears to its users as a single coherent system**.

两句话合起来，要素是四个：**便宜普通的机器**、**网络**、**分布式中间件**、**单机完不成的任务**。这些机器协同工作、共享系统资源，而用户看到的是**一台**整合的机器。

「看起来是一台」是字面意思，也是这个体系能给用户用的前提，术语叫透明性（*transparency*）。

### 七个特征

| 特征 | 说的是什么 |
| --- | --- |
| **Coherence**　一致性 | 整个集群对外表现为一个系统，不是一堆机器 |
| **Transparency**　透明性 | 用户不需要知道数据落在哪台机器、走哪条路径 |
| **Scalability**　可扩展性 | 加机器就能扩容，不用换架构 |
| **Availability**　可用性 | 部分节点坏掉，整体仍然能用 |
| **Integrity**　完整性 | 数据不丢、不错、不被改坏 |
| **Data Locality**　数据本地性 | 计算尽量靠近数据所在的那台机器 |
| **High Throughput**　高吞吐 | 单位时间能处理的数据量大 |

### 纵向扩与横向扩

Scale up纵向扩展买更强的机器：更快的 CPU · 更大的内存 · 更多的盘

Scale out横向扩展加更多机器：便宜的普通服务器 × N

分布式系统走的是横向扩展。**用数量换单机性能**，一台坏了换一台，代价是必须处理协调、容错和一致性问题。后面 HDFS 里的副本、心跳、机架感知，都是为这几个问题付的账。

### 分布式文件系统

它做的是一件事：跨多台计算机或服务器**管理文件与目录**。数据存在集群里的多个节点上，同时允许多个用户访问这些数据。

支撑它的关键技术有六项。

| 关键技术 | 解决什么 |
| --- | --- |
| **命名空间**<br>*namespace* | 用统一命名空间（也就是目录树）定位文件，用户按路径访问 |
| **副本管理机制**<br>*copy management* | 一份数据存多份，机器坏了还有别的副本顶上 |
| **并发与数据完整性**<br>*concurrency / integrity* | 多人同时读写时，数据仍然是完整的 |
| **数据访问机制**<br>*data access* | 客户端怎么找到数据、怎么拿到数据 |
| **安全机制**<br>*safety* | 谁能读、谁能写 |
| **规模机制**<br>*scale* | 集群变大时，管理开销不能跟着失控 |

HDFS 就是照这套骨架造出来的。下一节能看清：**命名空间落在 NameNode 上，副本落在 DataNode 上。**

### 评价一个分布式系统，看六个维度

| 维度 | 翻译成人话 |
| --- | --- |
| Performance　性能 | 同样的事，多久能做完 |
| Fault Tolerance　容错 | 坏了几台，还能不能继续 |
| Scalability　可扩展性 | 数据涨十倍，加机器顶不顶得住 |
| Openness　开放性 | 能不能接别的工具、别的格式 |
| Cost-effective　性价比 | 每 TB 存一年花多少钱 |
| Flexibility　灵活性 | 数据类型变了，要不要重做一遍 |

> **存了就不删**
>
> ① 大数据的存储是「**只追加不删除**」，这决定了后面所有架构的形状；<br> ② 分布式系统的定义落在最后半句，**对用户像一台机器**；<br> ③ 分布式文件系统六项关键技术里，命名空间与副本分别落在主节点与从节点上。

> **总结**
> 1. **三层**：存储（只追加不删除）、计算（分布式提速）、挖掘（发现超越常识的关系与规律）。
> 2. **定义**：便宜普通的机器 + 网络 + 分布式中间件 + 单机做不到的任务；对用户是一台统一系统。
> 3. **七特征**：一致性、透明性、可扩展、可用性、完整性、数据本地性、高吞吐。
> 4. **两种扩展**：Scale up 换强机器，Scale out 加普通机器；分布式走后者。
> 5. **关键技术**：命名空间、副本管理、并发与完整性、数据访问、安全、规模。
> 6. **六维度**：性能、容错、可扩展、开放性、性价比、灵活性。

## 4.2　HDFS：把一千块硬盘拼成一个文件系统

> 一千台机器的硬盘，怎么组织成一个能用路径访问的文件系统？

### 从 Nutch 到 Hadoop

| 时间 | 发生了什么 |
| --- | --- |
| 2003 | Doug Cutting 启动 **Nutch** 项目，目标是处理数十亿次搜索、索引数百万网页 |
| 2003.10 | Google 发表 **GFS**（Google File System）论文 |
| 2004.12 | Google 发表 **MapReduce** 论文 |
| 2006 | Yahoo 与 Doug Cutting 团队基于 GFS 与 MapReduce 做出 **Hadoop** |
| 2008.01 | Yahoo 把 Hadoop 作为开源项目交给 Apache 软件基金会 |

Apache Hadoop 是一套开源软件，用来做可靠、可扩展的分布式计算。它要解决三件事：**海量数据的存储**（HDFS）、**海量数据的分析**（MapReduce）、**海量数据的组织**（HBase）。灵感来自 Google 的三篇论文：2003 年的 GFS、2004 年的 MapReduce、2006 年的 BigTable。

> **论文给的是方法，不是程序**
>
> Google 在论文里公开的只是处理方法，没有公开程序本身。所以提到 MapReduce，指的是一种处理方法，实现形式不止一种；提到 Hadoop，指的是按 Apache 协议开源发布的那个软件。

### 主从架构

HDFS 采用 **Master / Slave** 架构：一个集群里有一个 **NameNode**（主节点），其余节点全是 **DataNode**（从节点）。

客户端所有对 HDFS 的请求都是先向 NameNode 提的，**HDFS 的内部工作机制对客户端是透明的**。这句话解释了两条箭头：查目录走 ①，搬数据走 ④，中间不经过 ②③ 那条链路。

### Block：存储的基本单位

数据按**块**（*block*）分散存放在各个 DataNode 上。Apache Hadoop 2.x 的默认块大小是 **128 MB**，1.x 是 64 MB。这个大小可以自己指定。

块是元数据的最小记账单位：NameNode 记的是「某个块的几份副本在哪几台机器上」，不需要记每个字节的位置。所以块选多大，直接决定元数据有多少条。

### NameNode 记什么

- 管理文件系统的 **命名空间**，控制客户端对文件的访问；
- 维护并管理所有 DataNode（从节点）；
- 记录集群里所有文件的 **元数据**，包括块存放的位置、文件大小、权限、层级结构；
- 记录文件系统元数据上发生的 **每一次变更**；
- 定期接收所有 DataNode 的 **心跳** （heartbeat）和 **块报告** （block report），确认它们还活着。

元数据分三部分：**命名空间**、**文件到文件块**的对应、**文件块到 DataNode** 的映射。落地成两个文件。

| 文件 | 里面是什么 |
| --- | --- |
| **FsImage** | NameNode 启动以来文件系统命名空间的**完整状态** |
| **EditLogs** | 相对最近一次 FsImage 发生的**所有修改** |

两个文件的关系就是「底片 + 底片之后拍的新照片」。FsImage 是某个时刻的全量，EditLogs 是之后的增量。增量越积越多，启动就越慢，所以要有人定期把增量合进全量。

### SecondaryNameNode 不是备份

这名字骗人。它是与主 NameNode 并发工作的**帮手守护进程**（helper daemon），不是备用的 NameNode，主节点挂了它顶不上。

它做的事是 **checkpoint**：定期从 NameNode 下载 EditLogs，应用到 FsImage 上，生成新的 FsImage，再把这个新 FsImage 回传给 NameNode，供 NameNode 下次启动时使用。

换句话说，它替代的是**合并**这件重活，让主节点不用一边服务一边合并。

### DataNode：数据真正待的地方

- 跑在 **commodity hardware** 上，也就是便宜、不高端的普通机器，不保证高可用；
- 真实数据存在这里；
- 执行文件系统客户端发来的底层读写请求；
- 定期向 NameNode 发心跳报告整体健康状况，**默认 3 秒一次**。

### 副本与机架感知

块要靠**副本**（*replica*）提供容错，默认副本因子是 **3**，可以配置。NameNode 定期从 DataNode 收块报告来维护副本数，某个块的副本多了就删，少了就补。

光有 3 份还不够，副本放在哪很关键，这由**机架感知**（*rack awareness*）算法决定：

1. 第一份副本放在 **本地机架**；
2. 接下来两份放在 **不同（远程）机架** 上，而且必须是那个机架里的 **不同 DataNode**；
3. 剩下的副本随机放，但尽量保证 **同一个机架上不超过两份**。

### 写一次，读多次

HDFS 遵循 **Write Once Read Many**：文件写进去之后**不能修改**。这一条决定了它的读写流程长什么样。

| 操作 | 流程 |
| --- | --- |
| **写** | 先与 NameNode 通信，确认允许写，并拿到接收文件块的 DataNode；然后客户端把文件块传给对应的 DataNode；收到块的 DataNode 再把副本转发给其他 DataNode |
| **读** | 客户端把文件路径发给 NameNode，收到文件元数据；按元数据找到对应的 DataNode，逐块取回，在本地拼接成完整文件 |

写流程里，**副本是 DataNode 之间接力传的，不是客户端传三份**。客户端只传一次，链上的节点各自往下传。

### 一条元数据长什么样

```text
NameNode (FileName, replicas, block-ids, id2host...)

/test/a.log, 3, {blk_1, blk_2}, [{blk_1:[h0,h1,h3]}, {blk_2:[h0,h2,h4]}]
```

读法是：文件 `/test/a.log`，3 份副本，切成两块；`blk_1` 在 h0、h1、h3 上，`blk_2` 在 h0、h2、h4 上。一条记录就把「文件怎么切、切完放哪」说完了。

### 什么时候不该用 Hadoop

| 场景 | 为什么不适合 |
| --- | --- |
| **低延迟的数据访问** | 要快速访问数据里的一小部分，HDFS 的强项是吞吐不是延迟 |
| **需要频繁修改数据** | 它适合以读为主、不改数据的情形 |
| **大量小文件** | 它适合「文件少而大」的场景 |

> **HDFS 的三条设计**
>
> ① **职责分开**：NameNode 管元数据与命名空间，DataNode 存真实数据块；<br> ② **两份保险**：副本因子 3 解决「块丢了」，机架感知解决「整个机架没了」；<br> ③ **一次写多次读**：写完不能改，所以写走接力、读走并行取块。

> **总结**
> 1. **来历**：2003 Nutch → 2003.10 GFS 论文 → 2004.12 MapReduce 论文 → 2006 Yahoo 做 Hadoop → 2008.01 交给 Apache。
> 2. **三件事**：存（HDFS）、算（MapReduce）、组织（HBase）；灵感来自 GFS、MapReduce、BigTable 三篇论文。
> 3. **架构**：一个 NameNode + 多个 DataNode；客户端只找 NameNode，内部机制透明。
> 4. **块**：2.x 默认 128 MB，1.x 是 64 MB，可配置。
> 5. **元数据**：命名空间、文件到块、块到 DataNode；落地为 FsImage（全量）与 EditLogs（增量）。
> 6. **SecondaryNameNode**：帮手，做 checkpoint 合并，**不是备份**。
> 7. **DataNode**：普通机器，存真数据，默认 3 秒心跳。
> 8. **副本**：默认 3 份；第一份本地机架，后两份跨机架不同节点，其余随机且同机架不超过两份。
> 9. **读写**：Write Once Read Many；写时 DataNode 接力传副本，读时逐块取回本地拼接。
> 10. **不适用**：低延迟小数据访问、频繁修改、大量小文件。

## 4.3　从关系库到 NoSQL

> 关系型数据库用了四十多年，为什么大数据要另起一套？

### 关系库的好与不好

| 优点 | 缺点 |
| --- | --- |
| 支持 **ACID** | 数据量大、并发读写高的时候表现不好 |
| 二维表，模型清楚 | 不适合数据类型不断变化的应用场景 |
| 复杂查询能力强 | 频繁操作代价大，简单处理效率低 |
| 冗余低 |  |
| 稳定 |  |

ACID 是四个基本特性。**原子性**（*Atomicity*）：要么全做，要么全不做。**一致性**（*Consistency*）：从一个合法状态到另一个合法状态。**隔离性**（*Isolation*）：并发事务互不干扰。**持久性**（*Durability*）：提交了就落盘，断电不丢。

这四条是关系库的立身之本，也是它在分布式环境里最贵的地方。要让多个节点上的多份数据同时满足 ACID，协调成本会随节点数上升。

### NoSQL 是什么

**NoSQL** 读作 *Not Only SQL*，不是「不要 SQL」。它指的是**非关系型、分布式、开源、可横向扩展**的下一代数据库管理系统，通常**不保证遵循 ACID**。

它能同时处理结构化与非结构化数据，也能较快地处理非结构化数据和大数据。对数据管理目的的认识也变了，尤其是对「一致性怎么保证」这一点的看法。

> **它是补充，不是替代**
>
> 提出 NoSQL 的目的是给关系数据库提供一种补充方案。需要强事务、复杂 join 的场景，关系库仍然是首选。

### 时间线

| 年份 | 事件 |
| --- | --- |
| 1998 | Carlo Strozzi 使用 NoSQL 这个词 |
| 2000 | Neo4j 图数据库发布 |
| 2004 | Google 推出 BigTable |
| 2005 | CouchDB 发布 |
| 2007 | Amazon Dynamo 研究论文发表 |
| 2008 | Facebook 开源 Cassandra 项目 |
| 2009 | NoSQL 一词被重新提起 |

### CAP 定理与 BASE

**CAP**（也叫 Brewer 定理）说三个性质不能同时满足。

| 性质 | 含义 |
| --- | --- |
| **一致性**<br>*Consistency* | 所有节点上的数据在同一时刻是一致的 |
| **可用性**<br>*Availability* | 每个请求都能拿到响应 |
| **分区容忍**<br>*Partition Tolerance* | 网络断开、节点分成几块时，系统仍能继续工作 |

分布式系统的网络本来应该是连通的，但故障会让某些节点之间不通，整个网络分成几块区域，数据就散在这些不连通的区域里，这叫**分区**。

如果一个数据项只存在一个节点上，分区一出现，跟它不连通的那部分就访问不到这个数据，这种分区就是无法容忍的。**提高分区容忍性的办法是把数据复制到多个节点**，分区之后这个数据项在每一块区域里都有一份。但复制又带来一致性问题：多份数据可能不一致。要保证一致，每次写操作都得等**全部**节点写成功，等待本身又伤可用性。

所以实际系统在 C 与 A 之间做取舍。放弃强一致的那条路叫 **BASE**。

| BASE | 含义 |
| --- | --- |
| **基本可用**<br>*Basically Available* | 允许损失部分可用性，保证核心功能能用 |
| **软状态**<br>*Soft State* | 允许系统存在中间状态 |
| **最终一致**<br>*Eventually Consistent* | 不要求时刻一致，只要求最终一致 |

### 四类 NoSQL

| 类型 | 怎么存 | 代表 |
| --- | --- | --- |
| **键值存储**<br>*key-value* | 每一项存成一个 key（或属性名）加一个 value | Redis、Memcached |
| **文档型**<br>*document* | 每个 key 配一个叫「文档」的复杂结构，可带键值对、键数组、嵌套文档 | MongoDB、CouchDB |
| **宽列存储**<br>*wide-column* | 不按行存，把同一列的数据存在一起 | HBase、Cassandra、BigTable |
| **图存储**<br>*graph* | 存数据之间的网络关系，比如社交关系 | Neo4j |

这四类和关系库的根本差别在建模单位。关系库以**元组和关系**为单位，NoSQL 改为支持数据对象的多样性与复杂性：**支持数据对象嵌套，也支持存放列表数据**。

### 相对关系库的三个优势

1. 易于数据的 **分散存储与处理**；
2. 数据频繁操作的成本低，简单处理效率高；
3. 适用于 **数据模型不断变化** 的应用场景。

> **NoSQL 的边界**
>
> ① 关系库卡在「大数据量高并发」和「模型常变」这两处；<br> ② NoSQL 是**补充方案**，读作 Not Only SQL，不保证 ACID；<br> ③ CAP 三者取二，放弃强一致就走 **BASE**：基本可用、软状态、最终一致。

> **总结**
> 1. **关系库**：ACID、二维表、复杂查询、低冗余、稳定；弱在高并发大数据量、类型常变、频繁操作。
> 2. **NoSQL**：Not Only SQL；非关系、分布式、开源、可横向扩展；不保证 ACID；是补充不是替代。
> 3. **CAP**：一致性、可用性、分区容忍不可兼得；复制提分区容忍，等待全副本则伤可用性。
> 4. **BASE**：基本可用、软状态、最终一致。
> 5. **四类**：键值、文档、宽列、图；代表分别是 Redis、MongoDB、HBase / Cassandra、Neo4j。

## 4.4　HBase：按列存的大表

> 一张表有上亿行、上百万列，换个数据库就能存下吗？

### HBase 的定位

- Apache Hadoop 项目的 **子项目**；
- 构建在 **HDFS** 之上的可扩展、高可靠、高性能分布式数据库；
- 主要用来存 **非结构化与半结构化** 的松散数据；
- 采用 **BigTable** 的数据模型；
- **按列而不是按行** 组织；
- 对大规模数据提供 **随机、实时** 的读写访问。

最后两条是它存在的理由。HDFS 擅长顺序扫大文件，但不擅长「按主键查一行」；HBase 补的正是这块。

### HBase 站在 HDFS 上面

HDFS 保证的是「字节放得下、不丢」，它不提供按主键定位的能力。想在十亿行里取第 7 亿行，HDFS 只能从头扫到那里。HBase 在前面加了一层按行键组织的索引，数据本身仍然躺在 HDFS 的块里。

### 行式与列式：差别在存储机制

两种存储机制不一样：行式把一行的字段挨着放，列式把同一列的值放在一起。

| 操作 | 行式存储 | 列式存储 |
| --- | --- | --- |
| 取整行 | 一次连续读完，省事 | 要在多段之间跳着取 |
| 只取少数几列 | 整行都得读进来 | 只读用到的那几列 |
| 按列做权限 | 不好切分 | 天然按列（族）切分 |

### HBase 表的三条特征

1. **大表**：一张表可以有上亿行、上百万列；
2. **按列（族）存储和权限控制**，列（族）可以独立检索；
3. **稀疏表结构**：为空（null）的列 **不占存储空间**，所以表可以设计得非常稀疏。

第三条是列式带来的直接好处。行式里一行有一百个字段就要留一百个位置，列式里没值的列根本不写，稀疏表才存得下。

### 五个组成部分

| 组件 | 说明 |
| --- | --- |
| **Row Key**　行键 | 表按行键排序；行键就是主键，访问 HBase 表都走它 |
| **Column Family**　列族 | 建表时指定，是 schema 里的键值对 |
| **Column Qualifier**　列限定符 | 添加数据时动态指定；列的记法是 `<family>:<qualifier>` |
| **Cell**　单元格 | 由 `(row, column, version)` 三元组唯一确定 |
| **Time Stamp**　时间戳 | 每个单元格都有自己的元数据，版本靠它区分 |

> **建表只定到列族**
>
> 建表时只指定**表名**和**列族名**，列限定符等到写数据时才确定。这是 HBase 与关系库在建表这一步最大的差别：关系库要求先把字段全部定死。

列的完整写法是 `族:限定符`，中间一个冒号。写 `info:name` 是指列族 `info` 下面的 `name` 这一列。只写 `info` 则表示整个列族。

列族的名字要能放进文件名里，所以只能用可见字符，冒号、斜杠这类符号不能出现在族名里。一张表通常一到三个列族，多了会让「读一行」变成跨多个 Store 拼装。

这条设计把「改」变成了「再写一次」。关系库的 update 覆盖旧值，HBase 的 put 在链头插一条新的，读的时候取链头。旧值不会立刻消失，等后台合并（*compaction*）时才按规则丢弃：留几条由列族的 `VERSIONS` 决定，活多久由 `TTL` 决定。

所以 `put` 既是插入也是更新。判断是不是同一行看行键，判断是不是同一列看 `族:限定符`，判断是哪一次写看时间戳。

### 行键：既是主键，也是排序键

行键（*row key*）在 HBase 里承担三件事：唯一标识一行、决定这一行排在哪、决定这一行落在哪个 Region。前两件在逻辑层，第三件直接决定集群的负载是否均衡。

排序用的是**字节序**（*byte order*）。这一点最容易踩：写成字符串的编号，`'100'` 排在 `'99'` 前面。要按数值排，得把数字补成定长，或者用定长二进制。

行键的长度有实际代价。它会被反复写进每个 HFile 的索引里，几十字节的行键在上亿行上就是几个 GB 的内存占用。习惯做法是控制在几十字节以内，公共前缀尽量短。

真正麻烦的是热点。行键单调递增时（时间戳、自增 ID 打头），新写入会全部落在同一个 Region 上，一台机器忙不过来，其余机器闲着。

打散的办法有三种。**加盐**（*salting*）在行键前面拼一段固定长度的散列值，范围扫描从一次变成三次。**哈希**把整段换成散列值，分布最均匀，但完全失去顺序。**反转**把行键倒过来写，只对定长的数字键有效。

*Client、HMaster、ZooKeeper 与三个 RegionServer 的位置关系，以及每个 RegionServer 内部的 Region、Store 与 HLog。*

| 组件 | 职责 |
| --- | --- |
| **Client** | 发起读写；自己缓存 Region 位置，下次直接连 RegionServer |
| **ZooKeeper** | 记录集群状态：谁是 HMaster、哪些 RegionServer 在线、`hbase:meta` 在哪台机器 |
| **HMaster** | 分配与迁移 Region、建表删表、负载均衡；不存数据，不接读写请求 |
| **RegionServer** | 真正干活的进程：承接读写、管理 Region、刷写与合并 |
| **Region** | 表按行键切出的一段区间，是负载均衡的最小单位 |
| **Store** | 一个列族对应一个 Store，里面是 MemStore 加若干 StoreFile |
| **HLog** | 预写日志（*WAL*，write-ahead log），一台 RegionServer 共用一份 |

第一次访问的路径长一点。Client 先在 ZooKeeper 上找到 `hbase:meta` 的位置，从 meta 表查到行键落在哪个 Region、那台 RegionServer 是谁，然后直连过去，并把这一段缓存下来。后面的读写都跳过 Master。

HMaster 挂掉不影响现有读写，只影响建表、改表和 Region 的重新分配。它管的是拓扑，数据通路不经过它。

*从定位 Region 到 compact 合并的五个阶段。*

第二步先写日志是为了防丢。数据刚进内存时机器断电，内存里的东西就没了；HLog 已经落到磁盘，重启时重放一遍能补回来。这一步有磁盘写，但它是顺序写。

第三步写 MemStore，它是内存里按行键排好序的结构。走到这里 put 命令就返回了，所以 HBase 的写延迟低到毫秒级。

第四步 flush：一个 Store 的 MemStore 到阈值（默认 128 MB）就整体刷成一个 HFile。HFile 写完之后不再修改，这个只读性质让后面的读取不需要加锁。

第五步 compact 分两种。小合并（*minor compaction*）把几个小 HFile 合成一个，不动内容；大合并（*major compaction*）把一个 Store 下的所有 HFile 合成一个，顺便清掉标记删除的数据和超过 `VERSIONS` 的旧版本。大合并很吃 IO，线上一般在低峰期手动触发。

*一条 get 请求依次经过 BlockCache、MemStore、HFile，命中即返回。*

BlockCache 缓存最近读过的数据块，热数据基本都在里面。MemStore 里是还没落盘的新数据。剩下的落到 HFile 上找，而一个 Store 可能有好几个 HFile，最坏情况要全翻一遍。

布隆过滤器（*Bloom Filter*）在这里挡一道。每个 HFile 带一份摘要，能确定「这个行键不在我这儿」，就不必打开文件。建表时写 `BLOOMFILTER => 'ROW'` 开的就是这个。

读比写慢，原因就是这个不对称：写只进内存，读要找三处再合并。表越大、HFile 越多，读放大越明显。大部分调优手段都指向同一件事，减少一次读要翻的文件数。

*一个 Region 写到阈值后自动分成两个，各自继续接收写入。*

分裂是自动的，不需要停机。新分出来的 Region 未必留在原机器上，HMaster 会看各台负载决定搬不搬。单台 RegionServer 上的 Region 数一般控制在几十到一百多，太少了内存用不满，太多了管理开销大。

热点行键会让分裂失去意义：分出来的两个 Region 还落在同一台机器上，写压力没有变化。这是行键设计重要的另一半理由。

### 和关系库摆在一起比

| 维度 | 关系库 | HBase |
| --- | --- | --- |
| 数据模型 | 行与列，schema 先定死 | 行键加列族，列随写随加 |
| 存储方式 | 按行存 | 按列族存，物理上拆成多张表 |
| 扩展方式 | 纵向加配置；横向要分库分表，应用得跟着改 | 横向加机器，Region 自动迁移 |
| 查询方式 | SQL，支持 join、聚合、子查询 | 按行键 get，按区间 scan |
| 事务 | 跨行跨表，强一致 | 单行原子，没有跨行事务 |
| 索引 | 可以建多个二级索引 | 只有行键一个索引 |
| 适合的数据量 | GB 到 TB | TB 到 PB |

「只有行键一个索引」这一条决定了它的用法。业务上要按别的字段查，办法是把那个字段拼进行键，或者另建一张索引表，用行键存「字段值到主键」的映射。这笔账要提前算。

### 适用场景

- 存储大数据量，几百 TB 的量级；
- 需要 **高写入吞吐**；
- 需要在海量数据里做高效的 **随机访问**，也就是按 key 查；
- 需要随数据量 **平滑扩展**；
- 数据是非结构化或半结构化的；
- **不需要完整的 RDBMS 能力**，比如跨行跨表事务和 join。

最后一条是门槛。要 join、要事务，HBase 不是合适的地方。

> **HBase 的模型**
>
> ① 建在 HDFS 上，用 BigTable 的模型，**按列族存**，随机读写靠行键定位；<br> ② 五层模型里，**行键排序、列族建表时定、限定符随写随加**，单元格带时间戳可存多版本；<br> ③ 逻辑一张表，物理按列族拆表，空列不占空间；<br> ④ 写先进 HLog 与 MemStore，再刷成 HFile；读要合并 BlockCache、MemStore、HFile 三处。

> **总结**
> 1. **定位**：Hadoop 子项目，建在 HDFS 上，存非结构化与半结构化松散数据，按列存，支持随机实时读写。
> 2. **表特征**：上亿行上百万列；按列族存储与权限控制、列族独立检索；稀疏，null 不占空间。
> 3. **五组件**：Row Key（主键、排序）、Column Family（建表时定）、Column Qualifier（写入时定）、Cell（row + column + version）、Time Stamp（版本）。
> 4. **两视图**：逻辑视图是一张表；物理视图按列族拆开，每行是「行键 + 限定符 + 时间戳 + 值」。
> 5. **架构**：Master 管拓扑不管数据；RegionServer 管读写；表按行键切成 Region，一个列族一个 Store，一台机器一份 HLog。
> 6. **读写路径**：写先 WAL 再 MemStore，满了刷 HFile，后台 compact；读依次查 BlockCache、MemStore、HFile。
> 7. **适用**：几百 TB、高写入吞吐、按 key 随机访问、平滑扩展、半结构化或非结构化、不需要跨行事务与 join。

## 4.5　HBase Shell：把表建起来、数据写进去

> 命令行敲一条命令，表里到底发生了什么？

HBase 自带一个基于 JRuby 的交互式命令行，叫 **HBase Shell**。它把 Java API 包成一组命令，建表、写数据、查数据、删表都能在里面完成。这一节按操作的先后顺序走一遍，每条命令写清参数、执行结果，以及执行之后表变成了什么样。

标题旁标了主线的几节，是从建表到删表这一整轮里每次都会敲的命令。没标的几条偶尔才碰一次，语法查得到就行，放在最后一起讲。

### 启动：三个东西的先后顺序主线

HBase 的数据存在 HDFS 上，所以 HDFS 必须先起来。

```bash
$ cd /usr/local/hadoop
$ ./sbin/start-dfs.sh          # 先起 HDFS
$ jps                          # 应该看到 NameNode、DataNode、SecondaryNameNode

$ cd /usr/local/hbase-1.1.2
$ ./bin/start-hbase.sh         # 再起 HBase，它会连刚才那个 HDFS
$ jps                          # 多出 HMaster、HRegionServer

$ ./bin/hbase shell            # 进命令行，提示符变成 hbase>
```

顺序反了会起不来。HDFS 还没准备好就启动 HBase，RegionServer 会因为写不了 HLog 而退出。

| 进程 | 对应组件 |
| --- | --- |
| `NameNode` | HDFS 的主节点，管目录树和块映射 |
| `DataNode` | HDFS 的从节点，真正存块 |
| `HMaster` | HBase 的主节点，管 Region 分配 |
| `HRegionServer` | HBase 的从节点，接读写 |

图形界面在 16010 端口（1.0 以前是 60010）。浏览器打开 `http://localhost:16010/` 能看到 Master 状态、RegionServer 列表和每张表的 Region 分布。这个地址只在本机有效，从外部访问要改绑定。

### 建表：create主线

语法是表名加一到多个列族定义。列族定义写成一个大括号里的键值对，箭头 `=>` 是 Ruby 的散列写法，键名要大写。

```bash
create '表名', \
       {NAME => '列族1', VERSIONS => 版本数}, \
       {NAME => '列族2', VERSIONS => 版本数}
```

行尾的反斜杠表示命令没写完，Shell 会接着收下一行。

只给列族名是最简写法，其余参数全用默认值。

```bash
hbase> create 'people_zs', {NAME => 'info', VERSIONS => 3}, \
                       {NAME => 'data', VERSIONS => 1}
0 row(s) in 1.2 seconds

=> Hbase::Table - people_zs
```

同一件事也可以写成 `create 'people_zs', 'info', 'data'`。两种写法等价，后者不能分别指定版本数。

表名后面挂一截自己的标识，是个好习惯。多人共用一台机器时表名会撞，撞了以后 `drop` 掉的可能不是自己那张。

| 列族参数 | 含义 |
| --- | --- |
| `NAME` | 列族名，必填 |
| `VERSIONS` | 保留几个版本，默认 1，即只留最新值 |
| `TTL` | 数据的存活秒数，超时在合并时清掉，默认永久 |
| `BLOOMFILTER` | 布隆过滤器类型，`NONE` / `ROW` / `ROWCOL`，默认 `ROW` |
| `BLOCKCACHE` | 是否进读缓存，默认 `true` |
| `COMPRESSION` | 压缩算法，`NONE` / `GZ` / `SNAPPY` 等 |
| `IN_MEMORY` | 是否优先常驻内存，小表可以打开 |

表级别的参数写在列族定义后面，常见的是预分区。

```bash
hbase> create 'people_zs', {NAME => 'info'}, SPLITS => ['rk1000', 'rk2000']
```

这条建表语句一建好就有三个 Region，边界是 `rk1000` 与 `rk2000`。数据量一开始就很大时，预分区能避免所有写入先挤在一个 Region 上。

### 看表：list 与 describe主线

```bash
hbase> list
TABLE
people_zs
student
2 row(s) in 0.02 seconds

hbase> describe 'people_zs'
Table people_zs is ENABLED
COLUMN FAMILIES DESCRIPTION
{NAME => 'data', VERSIONS => '1', TTL => 'FOREVER', BLOOMFILTER => 'ROW', ...}
{NAME => 'info', VERSIONS => '3', TTL => 'FOREVER', BLOOMFILTER => 'ROW', ...}
2 row(s) in 0.05 seconds
```

`describe` 的输出看三处就够：第一行的 `ENABLED` 是表的状态，`NAME` 是列族名，`VERSIONS` 是保留的版本数。后面那一长串 `BLOCKCACHE`、`COMPRESSION` 都是默认值，不用逐条记。

两个列族 `info` 和 `data` 都在，说明建表成功了。少一个，八成是大括号或逗号写错，命令只执行了一部分。

### 写数据：put主线

语法是四个必填参数加一个可选的时间戳。

```bash
put '表名', '行键', '列族:限定符', '值'
put '表名', '行键', '列族:限定符', '值', 时间戳
```

时间戳省略时由服务器取当前毫秒数，所以平时只写四个参数。

```bash
hbase> put 'people_zs', 'rk0001', 'info:name', 'MaYun'
0 row(s) in 0.14 seconds

hbase> put 'people_zs', 'rk0001', 'info:gender', 'male'
hbase> put 'people_zs', 'rk0001', 'data:myurl', 'www.yun.alibaba.com/myURL'
hbase> put 'people_zs', 'rk0002', 'info:name', 'LiuChangle'
```

四条命令之后表里有两行。注意 `rk0001` 这一行的三个单元格分属两个列族，`info` 下面两个、`data` 下面一个。

| 行键 | info:name | info:gender | data:myurl |
| --- | --- | --- | --- |
| **rk0001** | MaYun | male | www.yun.alibaba.com/myURL |
| **rk0002** | LiuChangle | — | — |

> **列族必须已经存在**
>
> `put` 能随手加列限定符，但**加不了列族**。往一个不存在的列族里写，会直接报 `ColumnFamilyNotFoundException`。列族是建表时定死的，要加得用 `alter`。

### 读数据：get主线

`get` 按行键取，一条命令最多返回一行。第三个参数指到哪一层，就取到哪一层。

```bash
get 'people_zs', 'rk0001'                      # 整行
get 'people_zs', 'rk0001', 'info'              # 一个列族
get 'people_zs', 'rk0001', 'info:name'         # 一个单元格
```

要历史版本，把列名和版本数一起写进大括号。

```bash
get 'people_zs', 'rk0001', \
    {COLUMN => 'info:name', VERSIONS => 3}
```

```bash
hbase> get 'people_zs', 'rk0001'
COLUMN                CELL
 info:gender          timestamp=1761804000123, value=male
 info:name            timestamp=1761804000101, value=MaYun
 data:myurl           timestamp=1761804000135, value=www.yun.alibaba.com/myURL
3 row(s) in 0.03 seconds
```

输出里 `3 row(s)` 实际是三个**单元格**，不是三行。这个措辞容易误会，看到一次就记住了。

常用的还有两个方向，按时间范围取，或者按值筛选。

```bash
get 'people_zs', 'rk0001', \
    {COLUMN => 'info:name', TIMERANGE => [1761804000000, 1761804100000]}
get 'people_zs', 'rk0001', {FILTER => "ValueFilter(=,'substring:Ma')"}
```

第二种是过滤器（*filter*），写法是一串带引号的字符串。`substring` 表示 「值里包含」，`=` 表示等值比较。过滤器在 RegionServer 上执行，只把命中的结果传回来。

### 扫描：scan主线

`scan` 按行键顺序走，从第一行开始，可以限定区间、列和条数。

```bash
scan 'people_zs'                                            # 全表
scan 'people_zs', {LIMIT => 5}                              # 只要前 5 行
scan 'people_zs', {STARTROW => 'rk0001', STOPROW => 'rk0003'}   # 行键区间
scan 'people_zs', {COLUMNS => ['info:name']}                 # 只要这一列
scan 'people_zs', {REVERSED => true}                       # 从最后一行往回走
```

区间是**左闭右开**：`STARTROW` 包含，`STOPROW` 不包含。上面那条能扫到 `rk0001` 和 `rk0002`，扫不到 `rk0003`。只想取 `rk0003` 一行，得把 `STOPROW` 写成 `rk0004`。

*同一张表上，get 覆盖一行，scan 覆盖一段连续区间，count 只数行数。*

三个读取命令的定位不同。`get` 走行键索引，一步到位；`scan` 顺着排序连续读，适合批量；`count` 只数行数，不看内容。

```bash
hbase> count 'people_zs'
2 row(s) in 0.11 seconds

hbase> count 'people_zs', INTERVAL => 1000
Current count: 1000, row: rk1000
...
10000 row(s) in 6.21 seconds
```

`count` 慢起来很慢。它先读每个 Region 的计数器估算，估算不准时退回逐行扫描，上百万行的表可能等几十秒。`INTERVAL` 的作用是每隔多少行报一次进度，至少不会让人以为命令卡死了。

hbase> deleteall 'people_zs', 'rk0001'

注意 `delete` 和 `deleteall` 的分工。`delete` 是 `put` 的反向操作，删的是某一列；`deleteall` 删的是整行。名字里的 all 指的是「这一行的所有列」，不是「所有行」。

两者都不会立刻回收磁盘。删除只是往 HFile 里写一条删除标记（*tombstone*），真正清掉要等大合并。所以删完再 `count`，数字变小了，磁盘占用却没变，这是正常的。

### 改数据：再 put 一次主线

HBase 没有 update 命令。改一个值就是往同一个单元格再 `put` 一次，服务器给它一个新的时间戳，新值成为链头。

```bash
hbase> put 'people_zs', 'rk0003', 'info:name', 'MaYun2'
hbase> put 'people_zs', 'rk0003', 'info:name', 'ZhaoZilong'

hbase> get 'people_zs', 'rk0003', 'info:name'
COLUMN                CELL
 info:name            timestamp=1761804060789, value=ZhaoZilong
1 row(s) in 0.02 seconds
```

默认只返回最新的一版。要把两条都看到，得显式要版本数：

```bash
hbase> get 'people_zs', 'rk0003', {COLUMN => 'info:name', VERSIONS => 3}
COLUMN                CELL
 info:name            timestamp=1761804060789, value=ZhaoZilong
 info:name            timestamp=1761804055112, value=MaYun2
2 row(s) in 0.03 seconds
```

两条都在，说明旧值没被覆盖。这也是为什么建表时 `VERSIONS` 要设成 3：设成 1 的话，合并之后旧版本就没了，改之前的值再也查不回来。

*ENABLED、DISABLED 与已删除之间的转换，以及 enable、disable、drop 三个命令的方向。*

为什么必须先 `disable`：Region 还在给客户端提供服务，直接删会让正在读的请求读到一半失去表。`disable` 先把 Region 下线、把 MemStore 里的数据刷盘，再删才安全。

忘了 `disable` 就 `drop`，会得到一条 `TableNotDisabledException`。这条报错很常见，改法就是先补一次 `disable`。

### 用得少的几条

下面这几条不在主线上，用到时照语法敲就行。

| 命令 | 用途 |
| --- | --- |
| `exists` | 判断表在不在，返回 `does exist` 或 `does not exist` |
| `enable` | `disable` 的反向，把表重新上线 |
| `truncate` | 清空数据、保留表结构，一步回到刚建好的样子 |
| `alter` | 改列族属性、加列族、删列族 |
| `incr` | 原子自增，返回 `COUNTER VALUE` |
| `append` | 原子追加，接在原值末尾 |

`alter` 能改属性、加列族，也能删列族。

```bash
alter 'people_zs', {NAME => 'info', VERSIONS => 5}
alter 'people_zs', NAME => 'extra'
alter 'people_zs', 'delete' => 'extra'
```

改已有列族的属性要先 `disable`，否则报 `TableNotDisabledException`。加列族可以不停表，改属性不行。

`incr` 和 `append` 在服务端一次完成读改写，客户端不用先 `get` 再 `put`。关系库做同一件事得开事务加行锁，HBase 没有跨行事务，单行的原子操作是有的。

### 非交互模式：把命令写成文件主线

命令多的时候，逐条敲容易错。可以把命令一行一条写进文本文件，让 Shell 一次执行完。

```bash
$ cat people_zs_commands.txt
create 'people_zs', {NAME => 'info', VERSIONS => 3}, \
                    {NAME => 'data', VERSIONS => 1}
put 'people_zs', 'rk0001', 'info:name', 'MaYun'
put 'people_zs', 'rk0001', 'info:gender', 'male'
scan 'people_zs'

$ ./bin/hbase shell people_zs_commands.txt
```

注意执行这个文件的位置：`hbase shell 文件名` 是在系统命令行里跑的，不是在 `hbase>` 提示符里面。在 Shell 里面执行文件用 `run '文件名'`，这是另一个命令。

加 `-n` 只检查语法不执行，改脚本时有用。

```bash
$ ./bin/hbase shell -n people_zs_commands.txt
```

### 常见报错对照

| 报错 | 原因 | 改法 |
| --- | --- | --- |
| `TableNotFoundException` | 表名写错，或表还没建 | 先 `list` 看一眼 |
| `TableNotDisabledException` | `drop` 前没 `disable` | 先 `disable` |
| `ColumnFamilyNotFoundException` | 往没建过的列族里写 | `describe` 核对列族名 |
| `Unknown argument` / 命令没反应 | 大括号没配对，或用了中文引号 | 全部换成英文单引号 |
| `count` 长时间不返回 | 全表逐行统计 | 加 `INTERVAL`，或改用 `scan` + `LIMIT` |
| 历史版本查不到 | 建表时 `VERSIONS` 是 1 | 建表时给 3，或 `alter` 改大 |

### 一条完整的流程

把上面的命令按顺序连起来，就是一次完整的建表到删表。下表左列是命令，右列是执行完之后表的样子。

| 命令 | 执行后表里有什么 |
| --- | --- |
| `create 'people_zs', {NAME=>'info', VERSIONS=>3}, {NAME=>'data', VERSIONS=>1}` | 空表，两个列族 |
| `put 'people_zs', 'rk0001', 'info:name', 'MaYun'` | 1 行 1 格 |
| `put 'people_zs', 'rk0001', 'info:gender', 'male'` | 1 行 2 格，info 下两列 |
| `put 'people_zs', 'rk0001', 'data:myurl', '...'` | 1 行 3 格，跨两个列族 |
| `put 'people_zs', 'rk0002', 'info:name', 'LiuChangle'` | 2 行 4 格 |
| `get 'people_zs', 'rk0001'` | 只读回 rk0001 的 3 格 |
| `scan 'people_zs'` | 两行按行键顺序列出 |
| `count 'people_zs'` | 返回 2 |
| `deleteall 'people_zs', 'rk0001'` | 只剩 rk0002 |
| `put 'people_zs', 'rk0003', 'info:name', 'MaYun2'` | 2 行，rk0003 有 1 格 |
| `put 'people_zs', 'rk0003', 'info:gender', 'male'` | rk0003 有 2 格 |
| `put 'people_zs', 'rk0003', 'data:myurl', '...'` | rk0003 有 3 格 |
| `delete 'people_zs', 'rk0003', 'info:gender'` | rk0003 剩 2 格 |
| `put 'people_zs', 'rk0003', 'info:name', 'ZhaoZilong'` | name 有两版，读到新的 |
| `get 'people_zs', 'rk0003', {COLUMN=>'info:name', VERSIONS=>3}` | 两条版本都出来 |
| `disable 'people_zs'` → `drop 'people_zs'` | 表消失，`list` 里没有了 |

> **Shell 的主线**
>
> ① 启动顺序：HDFS → HBase → `hbase shell`；<br> ② 建表只给表名和列族，列族可带 `VERSIONS`、`TTL`、`BLOOMFILTER`；<br> ③ 写用 `put`（四个必填参数），读用 `get`（一行）和 `scan`（区间，左闭右开）；<br> ④ 改就是再 `put` 一次，加 `VERSIONS => n` 才看得到旧版本；<br> ⑤ 删表先 `disable` 再 `drop`，删数据用 `delete`（一格）/ `deleteall`（一行）。

> **总结**
> 1. **启动**：`start-dfs.sh` → `start-hbase.sh` → `hbase shell`，`jps` 核对进程，16010 看界面。
> 2. **DDL**：`create`（表名 + 列族表）、`list`、`describe`、`exists`、`alter`、`disable` / `enable`、`drop`、`truncate`。
> 3. **写**：`put '表','行键','族:限定符','值'`；加不了列族，只能加限定符；时间戳由服务器补。
> 4. **读**：`get` 一行，可指定列族、列、版本、时间范围、过滤器；`scan` 区间为左闭右开，可 `LIMIT`、`REVERSE`；`count` 只数行，慢。
> 5. **删**：`delete` 删单元格，`deleteall` 删整行，`truncate` 清空表；都不立即回收磁盘。
> 6. **改**：再 `put` 一次即产生新版本，`VERSIONS => n` 查历史。
> 7. **非交互**：命令写进文本文件，`hbase shell 文件名` 一次执行，`-n` 只做语法检查。
